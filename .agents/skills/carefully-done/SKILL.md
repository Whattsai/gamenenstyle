# Carefully Done

此技能是核准 SD 之後的實作入口。不呼叫 `well-done` 接管，不繼承其不得停止規則。

## 核心規則

1. 先讀目標及涉及的其他工作區／服務／模組的 agent 指示、README、分析／設計／開發方法、相關文件與實際程式。
2. 讀使用者指定或 TDD 規劃交接列出的 MVP、完整 SPEC、BDD、TDD、持久化風險、使用者決策、缺漏回寫與注意事項；查核實際程式、測試、build/test/lint 命令、DB、前端、部署及全部相關工作樹改動。
3. 必讀 [SD 文件契約](.agents/skills/fantastic-design/references/document-contract.md)、[任務規劃規則](.agents/skills/fantastic-design/references/planning-rules.md)、[有序實作步驟契約](.agents/skills/fantastic-design/references/step-design.md) 及 [執行、同步與變更程序](references/execution-protocol.md)。不強制啟動多代理。
4. 設計核准、實際驗證及來源追溯是必要條件；不能因子技能自動補漏、一般重構或環境修復繞過確認關卡。
5. 每份工作包採用既定分項 SD 的完整結構，不將其改成一般工作包格式；命名、編號、來源 checkbox、進度、驗證紀錄、overview 與歸檔沿用目標專案慣例。

## Phase 1：選用與鎖定設計

先依完整 SPEC 定位 `docs/sd/<SPEC 完整名稱>/`，按完整設計批次計數，不按分項數量。

| 實際情況 | 固定行為 |
|---|---|
| 有 `final/` | 採用 final；不完整、過期或未確認時停止，列缺項，不自動退回候選。 |
| 無 final，只有一套未被明確取代的候選 | 選用該套；仍須核准、完整性及基準查核通過。 |
| 無 final，兩套以上候選 | 通知使用者指定具體批次，或選用 `design-decision`；未決定不開工。 |
| 無設計 | 通知先完成 `fantastic-design`。 |

歷史批次只有明確記為已取代才能排除；不完整批次必須揭露並取得處置，不能靜默忽略以湊唯一候選。使用者已有效指定候選時沿用該決定；有 final 仍依 final 優先規則，不在途中自動切換。

選定後讀全部總覽、系統設計、追溯矩陣、分項及 final 決策紀錄。查核：

- 原 TDD `Ready for well-done`、來源可讀、風險已確認、缺漏已回寫、無未解除阻斷。
- SD 固定範本完整、核心設計已定、全部 SPEC／BDD／TDD 設計涵蓋且跨包責任清楚。逐條查 BDD 條件／觸發／結果及適用畫面、元件、互動、狀態與平台均有實際產品檔案／符號、具體邏輯、F／S／I／V；單純測試映射或泛指模組不是完整設計，停止開工並回到設計確認。純驗證／既有沿用須有具體理由及產品位置。
- 每份分項的有序步驟完整，I／步驟／檔案／驗證映射有效，前置無循環；案例、命令、通過／停止條件足以執行。既有包缺步驟時先補設計並依確認規則更新核准，不由實作者現場猜補。
- 使用者已明確確認該文件包的具體設計版本，核准內容可還原，SD 交接為 `Ready for carefully-done`。已有效確認但未回填時可據實補紀錄，不重複詢問。
- 來源、程式基準、相關未提交改動與現況相容；先查核並保留有效既有成果，失效的核准／證據不能沿用。

任一必要條件不成立，保存缺項、白話影響與恢復條件，停止開工並請使用者處理。開始時在 SD 總覽鎖定包路徑、版本、來源與核准快照、執行責任；後續依賴該版本，不自動換包。

## Phase 2：按工作包逐項實作

1. 從既有依賴圖選取前置已滿足的下一包，再依順序表選取可開始的步驟；核對實際前置證據、共享契約、可寫檔案／符號、使用者改動與環境控制。不能因寫不同檔案就認定可安全並行。
2. 以目前步驟為執行單位，回讀其來源、I-ID、F-ID／V-ID、案例／斷言與通過／停止條件。執行適用 TDD 前完整讀取 [tdd-development](.agents/skills/tdd-development/SKILL.md)，按本步 Red（實際預期失敗）→ Green → 必要 Refactor → 回歸，以指定工作目錄與命令驗證；不讓子技能跨步驟或跨包接管全部清單。
3. 目前步驟涉及 UX 時先完整讀取 [bdd-frontend-ux-implementation](.agents/skills/bdd-frontend-ux-implementation/SKILL.md)，依核准的案例與操作驗證功能／畫面及適用平台。準備、整合、稽核或文件步驟執行其適用檢查，不強制製造 Red。既有核准已涵蓋的清單不再重複確認；新增或不同設計走變更關卡。
4. 每個子階段記錄實際命令／操作及結果；本步通過條件成立後才進入依賴它的下一步。失敗在本步設計內診斷修正並重驗；缺少必要前置或須改設計時停止，不自行補造案例、改斷言湊通過或跳步。
5. 每次驗證後依執行程序同步分項 SD、總覽、矩陣與對應 BDD／TDD；步驟只回填狀態及證據。全部必要步驟、I 驗收及指定整合驗證成立後才勾 I；該包必要驗收成立後才進入依賴它的包。保存當前步驟／子階段與副作用現況，恢復先查核再續作。

子技能的順序、範圍、自動補漏及「一定成功」規則受本技能與核准 SD 的邊界約束；一般持續執行授權不滿足缺少的設計決策。環境修復僅在既有設計與授權範圍內進行。

## 偏離設計的必要關卡

**已記載的檔案、邏輯、介面、資料、依賴、契約或驗證方式需要不同做法時，停止本需求後續實作，先與使用者討論。**

停止前保存原設計及證據、為何不能照案實作、實務情境與影響、建議／替代、影響的 SD／BDD／TDD、恢復條件及需重驗成果。引用本節與受影響設計的精確位置，說明確認必要的來源；不僅丟出技術名詞或要求泛泛同意。

確認後先更新設計版本、核准範圍及必要上游文件，重新查核追溯、基準與失效證據，再按新版本續作。同一次有效確認不重複要求。一般進度／證據回填，以及未受計畫限制且不影響設計的局部選擇可自行處理；不能以這些名義改掉已記載設計。

## Phase 3：整合與完整深度稽核

1. 按既定整合里程碑檢查目前產物的契約、資料流、依賴、共享責任及必要跨元件／回歸驗證；孤立包通過不等於整合通過。
2. 完整讀取 [spec-bdd-implementation-deep-audit](.agents/skills/spec-bdd-implementation-deep-audit/SKILL.md)，逐項比對全部 SPEC／BDD／TDD／SD／程式／測試／實際證據，不抽樣。檢查測試斷言及實際功能，不只看名稱或檔案存在。
3. 原設計內的實作／證據缺漏回寫負責包與原來源文件，在同一計畫補齊並重驗受影響項。需要新增／不同設計或改上游行為時先走確認關卡，不以稽核自動補漏直接實作。
4. 同步計數、checkbox、Sprint、里程碑、每日記錄、驗證與必要 overview。保留有效稽核證據，不因進入最終收尾重做一輪已完成稽核。

## Phase 4：交付與結案

主責人逐項核對完成契約、來源追溯、目前產物／版本與證據、文件同步、原定稽核及觸發的補漏／重驗，確認沒有持續寫入衝突。所有必要項目皆為 `Verified` 或有明確允許且證明同一條件的 `Accepted equivalent evidence` 才結案。

必要驗證缺環境或證據，保留 `Deferred`／`Incomplete`、原因、負責者與恢復條件；不得宣稱 100% 或以環境限制視為完成。來源歸檔只依原專案慣例與成立條件，保持追溯連結，不另建需求管理系統。

交付時列鎖定 SD 包／版本、相關 MVP／SPEC／BDD／TDD、主要改動與證據位置、實際執行的命令／操作及結果、重算後 SD 與來源進度、尚未驗收項／恢復條件。只改文件也至少執行 `git diff --check`；未執行的檢查明確說明。
