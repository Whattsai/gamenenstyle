# 按核准 SD 執行、證據同步與恢復

本程序與新流程的文件契約、規劃規則共同生效。以選定包的總覽及分項作為唯一執行紀錄，不另建平行管理文件。

## 每包起始

回讀該包原需求、設計、檔案清單、Todo 及驗證計畫；確認前置成果、契約版本、責任與可寫區段。查核目前實際檔案，包括使用者和其他執行者的未提交修改。未釐清重疊先保存證據與責任問題，不覆寫既有工作。

在有分工授權時，每位執行者只取得指定包／階段，收到來源、必要指示、允許檔案、排除範圍、契約版本、起始條件、檢查與共享資源控制及回傳格式。稽核工作仍可作流程內任務；最終整體驗收責任保留在主責人。不因支援不同 AI 設計就自行派工。

## 每步執行與結果判定

遵守 [有序實作步驟契約](../../fantastic-design/references/step-design.md)。每次選定步驟後：

1. 核對本步唯一負責 I、前置步驟／成果、F-ID／V-ID、契約版本及真實環境；讀取必讀檔案／符號及相關來源，確認可寫範圍。缺案例、命令、前置或重要邏輯時先記設計缺項，不自行補猜。
2. 按本步案例建立指定 fixture，明確記錄初始狀態、輸入、預期輸出／錯誤及副作用斷言。資料建立／清理、時間與亂數控制、外部服務替身或實際平台驗證均照已核准安排。
3. 在指定工作目錄執行本步操作。適用 Red 時，確認失敗來自預定的行為／斷言，或設計明列尚未建立的目標符號；依賴未安裝、錯目錄、環境不可用或無關編譯錯誤不能算預期失敗，也不能據此直接 Green。
4. 在既定範圍完成 Green、必要 Refactor 及指定回歸，核對實際輸出、斷言及副作用。準備／整合／稽核／文件工作執行其適用檢查，不製造形式上的測試失敗。記錄各子階段的命令、版本、結果及證據。
5. 本步通過條件成立才標記可供下一步使用的成果。失敗在原設計內診斷修正並重驗；不得為求通過而放寬斷言、降門檻、跳步或擴大寫入。必要環境缺少保留原因及恢復條件；已寫明設計須改時停本需求後續實作，走確認關卡。
6. 更新步驟狀態、目前子階段、下一步與其起始條件；按下節同步。所有步驟只作原 Todo 的執行明細，不能另算進度或因個別步驟通過提前勾選 I／來源。

完成全包必要閱讀後，後續操作聚焦當前步驟及其相關來源、前置與共享契約；遇到跨包影響仍須回讀受影響設計。不得將焦點縮小當成略過全局前置或改寫核准設計的理由。

## 驗證與證據欄

按設計實際操作；UI 含互動、Loading、空、錯誤、導覽與要求的平台，不以編譯或元件檔存在代替畫面驗證。TDD 先記預期失敗與實際 Red，再記 Green 和必要 Refactor／回歸；既有完成項以現況及證據查核保留，不為重演流程破壞有效成果。

每個驗證列至少記：

- 驗證 ID、來源 SPEC／BDD／TDD、SD／I 葉節點、步驟 ID／子階段及驗收條件。
- 命令與工作目錄，或可重現的功能／畫面操作；測試資料及環境／平台／版本。
- 預期結果、實際結果、日期、exit code 或操作觀察、log／截圖／報告位置。
- 目前程式／測試路徑與必要行號、commit 加相關未提交改動或內容指紋。
- 驗收狀態、負責者、證據有效範圍；等價證據的明確允許依據，或未完成原因／恢復條件。

設計驗證、靜態檢查、桌面推演與實際產品執行分別標明。缺 E2E 平台時保留已通過的其他層，但不足以證明同一條件就維持 E2E `Deferred`；不得以替代檢查較容易執行就視為等價。

## 每次驗證後的同步順序

1. 在本步操作表及分項驗證表回填結果，檢查證據與目前版本相符。只有該 I 的全部必要步驟、I 驗收及指定整合驗證成立才更新 I 完成及分組；其餘只記實際執行狀態。D 葉節點保留設計完成證據，不隨 I 勾選一起變更。
2. 更新追溯矩陣的實作／測試／證據欄及整合狀態。對同一來源的多個包，檢查全部必要 I 集合及整合驗證，未齊前不勾來源完成。
3. 按來源原有慣例更新 BDD Scenario、TDD 測試項、驗證說明與原完成率；同步原文件的進度條、分層、Sprint、使用說明與最後更新等實際既有欄位。不能用 SD 子任務分母替代來源分母。
4. 彙總 SD 總覽的 D／I 分子分母、唯一 BDD／TDD 設計涵蓋及實際狀態，更新里程碑引用、每日記錄、下一步。不要重複計父項或摘要。
5. 變更影響既有證據時，列明原因、退回受影響的 I 與來源完成項為待驗，重算所有相關摘要；保留未受影響成果，不整包歸零。

## 變更討論與恢復

需要不同於任何已寫明設計的做法時，停止本需求後續實作；先保存可還原的現況與下列紀錄，不先做新方案再求追認：

| 必填資訊 | 寫入位置 |
|---|---|
| 原包、版本、設計章節及原做法 | 受影響分項的變更表 |
| 發現的程式／測試／平台證據，以及為何原案不能成立 | 同一變更列 |
| 白話實務情境、使用者效果與可能影響 | 同一變更列 |
| 建議、替代選項、影響 SD／SPEC／BDD／TDD、檔案、成本時程 | 同一變更列及總覽 |
| 恢復條件、待決策、失效證據與重驗集合 | 分項檢查點、矩陣及總覽 |

對使用者引用 carefully-done「偏離設計的必要關卡」與具體設計位置，說明為何須確認。取得明確決策後先回寫設計及必要上游、升版、保存新的核准範圍和可還原內容，再核對前置與來源追溯後恢復。未受影響核准維持有效；受影響內容由本次決策明確涵蓋，避免重複詢問。

中斷／交接時記任務 ID、實際執行者、已驗收／未驗收成果、可寫範圍與環境、停止原因、所需操作及可觀察恢復條件。恢復先驗證條件與實際工作樹；不把「已通知」當續作，不把「已續作」當驗收。責任轉移前確認舊寫入者已停止或隔離。

步驟層另記目前 S-ID／子階段、最後實際操作、已改檔案及內容版本、已建立資料／遷移／外部副作用、清理現況、待重驗及下一個操作。恢復時先對照事實，再決定從哪個子階段續作；不可為重演流程盲目重跑有副作用的命令，也不可憑中斷前的成功紀錄跳過已失效檢查。

## 稽核補漏與結案

完整逐項稽核的結果回寫原 BDD／TDD 及負責 SD。若只是核准設計已有要求但尚未實作／測試，可在原包補齊；新增檔案、改驗證方式或其他已記載細節均先走確認，不用「原設計內缺漏」概括豁免。

流程內稽核、修補與重驗都完成且證據有效後才最終收尾。收尾只核對完成契約與整體證據，具體新缺陷才重開受影響工作。報告須區分設計完成、設計涵蓋、實作驗證和來源自身完成率；任何必要 `Deferred`／`Incomplete` 都阻止全案結案。
