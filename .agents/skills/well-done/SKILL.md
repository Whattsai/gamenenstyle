# Well Done

此技能負責「開發到驗收」階段。使用此技能時，預設已完成 `perfect-plan` 或已有等效且經確認的 MVP、SPEC、BDD、TDD 文件包。

## 核心規則

1. 先閱讀工作目錄中的 `AGENTS.md` 或同等 agent 指示文件；若存在分析、設計、開發方法文件，也一併閱讀。
2. 讀取使用者指定或 TDD「規劃交接紀錄」列出的 MVP、SPEC、BDD、TDD 文件。
3. 每個階段開始前，讀取對應 `.agents/skills/{skill-name}/SKILL.md` 並遵守其流程；若子技能與本技能的自主開發規則衝突，以本技能為準，再以使用者最新明確要求為最高優先。
4. 涉及其他工作區、應用程式、服務、資料庫或外部模組時，先閱讀該目標範圍的 agent 指示、README、相關文件與實際程式碼，不得只依記憶或文件推測既有行為。
5. 文件語言、命名、路徑與格式遵循目前工作區既有慣例；若無明確慣例，使用使用者本次需求的語言。
6. 技術名詞、路徑、API、類別與方法名稱保留原文並使用 monospace。
7. 不要跳過需求追溯：每個 MVP/SPEC/BDD/TDD 項目都要能追到實作與測試證據。
8. 採最大幅度自動化；開發途中不得要求人工確認，不得以一般實作、測試、環境、交接缺漏、憑證、外部權限或需求不明作為停止理由，直到全部的開發項目全數完成。

## 前置條件

開始開發前，必須具備下列文件或等效輸入：

- MVP 需求文件。
- 一份或多份已確認的 SPEC 文件。
- 對應 BDD 文件。
- 對應 TDD 測試規劃。
- TDD 文件中的「規劃交接紀錄」；若缺失或不是 `Ready for well-done`，需停止並通知確認。
- 實作前風險與缺漏稽核結果已持久化到文件，且使用者已確認需補強項目。

若缺少上述文件，則不應繼續執行。

## 開發前交接自動修復

在讀到 TDD 文件後，先檢查「規劃交接紀錄」。未通過下列任一條件時，不得停止，必須自行修復或降級記錄後繼續：

- `交接狀態` 為 `Ready for well-done`。
- 文件包表格列出 MVP、SPEC、BDD、TDD 路徑，且檔案可讀取。
- 「已確認風險」中的每項風險都有使用者決策、文件回寫位置或接受原因。
- 「已補回缺漏」中的每項缺漏都有補入文件位置與狀態。
- 原交接紀錄列出的限制或阻斷項，皆已轉成自動修復策略、替代驗證或開發假設。

自動修復方式：

- 交接紀錄缺失：停止並通知確認。
- 狀態為 `Blocked`：停止並通知確認。
- 仍有 `待確認` 風險：停止並通知確認。
- 缺漏只存在交接紀錄：停止並通知確認。

## 自主開發規則

1. 不要在尚未完成所有開發項目前，以階段性進度作為交付或要求確認。
2. 沒有任何原因可以停止開發，任何問題皆需自行處理，直到全部的開發項目全數完成。

## Phase 1：開發前定位

1. 讀取 TDD 文件中的「規劃交接紀錄」，必要時執行交接自動修復。
2. 依交接紀錄讀取全部 MVP、SPEC、BDD、TDD 文件。
3. 讀取已持久化的實作前風險、缺漏回寫位置與實作注意事項。
4. 檢查目標程式碼、測試專案、建置命令、資料庫或前端目錄。
5. 建立內部實作順序，不需等待使用者確認。

## Phase 2：TDD 一次性開發完成

1. 讀取 `.agents/skills/tdd-development/SKILL.md`。
2. 依 TDD 文件執行 Red-Green-Refactor，完成所有 Unit、Integration、API、Frontend、E2E 或手動驗證清單。
3. 開發過程中自行處理測試失敗、編譯錯誤、缺漏依賴、命名不一致與文件不一致問題。
4. 完成整輪後，更新 TDD 進度、測試結果、實作檔案與可追溯證據。

## Phase 3：BDD 前端 UX 實作

1. 若 SPEC/BDD 涉及前端或 UI/UX，讀取 `.agents/skills/bdd-frontend-ux-implementation/SKILL.md`。
2. 本技能下，不在該技能的清單確認點暫停；直接依 BDD 與 SPEC 補充項目完成前端 UI/UX 實作。
3. 每個完成項目都要回寫 BDD 進度，並附實作檔案路徑與驗證方式。

## Phase 4：SPEC/BDD/實作深度稽核

1. 讀取 `.agents/skills/spec-bdd-implementation-deep-audit/SKILL.md`。
2. 逐項比對 SPEC、BDD、TDD、實作與測試，不得抽樣。
3. 對每項結論提供可追溯證據：文件路徑、程式碼路徑、測試路徑與必要行號。
4. 重算 TDD/BDD 完成度；不能沿用舊百分比。
5. 若完成度為 100%，進入 Phase 6 交付。
6. 若有缺漏，進入 Phase 5。

## Phase 5：缺漏補實作循環

1. 將深度稽核發現的缺漏回寫到 BDD/TDD：
   - 新增缺漏 Scenario 或補強測試。
   - 將無法追溯的 `[x]` 改回 `[ ]`。
   - 重新計算進度。
2. 回到 Phase 2 執行 `tdd-development` 補實作。
3. 依序再次執行 Phase 3 與 Phase 4。
4. 重複直到深度稽核確認需求、BDD、TDD、實作與測試皆為 100% 達成。

## Phase 6：交付驗收

最終回覆使用者時，列出：

- 本輪處理的 MVP / SPEC / BDD / TDD 文件。
- 新增或修改的主要程式碼與測試檔案。
- 已執行的驗證命令與結果。
- 深度稽核後的完成度與是否已達 100%。
- 若仍存在外部環境限制，列出已完成的本地替代驗證、已寫入文件的假設與後續人工回填項目；不得以阻斷作為結論。

## 驗證要求

1. 修改程式碼、資料庫、基礎設施或其他可執行資產時，先讀取目標工作區的 agent 指示或 README，依其建議命令執行 build/test/lint/migration 驗證。
2. 若目標工作區沒有明確驗證命令，依實際技術棧選擇最小但有意義的驗證，例如單元測試、整合測試、API 測試、前端測試、E2E 或手動驗證。
3. 只修改 Markdown 文件時，至少執行 `git diff --check`。
4. 驗證無法執行時，在最終回覆明確說明原因，不得以「應該可行」代替驗證。
