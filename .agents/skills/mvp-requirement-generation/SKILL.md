# MVP 需求文件生成流程

本技能協助將使用者撰寫的草稿需求（核心需求，格式不拘）轉換為正式的 MVP 需求文件，為後續 SDD 規格撰寫階段做準備。

## 前置條件

- 使用者已提供 MVP 草稿需求文件（`docs/requirements/MVP-XXX-*.md`）
- 草稿中至少包含核心功能描述

## 核心原則

### ⚠️ 絕對不可違反的規則

1. **完整保留原始需求**：來源 MVP 文件中的所有需求內容必須**完整保留**，不可簡化、刪減或改寫語意。此技能的目的是**補充揭露更多初步規劃資訊**，而非重新整理需求
2. **就地修改**：正式的 MVP 文件**直接修改在來源 MVP 文件**上，不另外產生新檔案
3. **設計問題優先**：如果需求存在明顯的設計問題（矛盾、不可行、遺漏關鍵限制），必須**立即停止生成**，列出議題與使用者討論確認後才可繼續
4. **使用者額外資料完整性**：若使用者在草稿中填寫了任何額外資訊（注意事項、設計特點、外部資料來源等），都必須**完整不可缺漏**地保留到正式 MVP 文件中

## 執行步驟

### 1. 閱讀 MVP 範本

閱讀 `.agents/skills/mvp-requirement-generation/assets/MVP-XXX-Template.md` 範本文件，理解正式 MVP 文件的標準結構。

### 2. 深入分析來源需求

仔細閱讀使用者提供的草稿 MVP 文件，識別：

- **核心功能清單**：列舉所有功能項目
- **功能間依賴關係**：是否存在功能間的先後順序或依賴
- **業務規則與限制**：明確的商業邏輯約束
- **技術限制或特殊需求**：指定的技術方案、框架、架構參考
- **使用者額外補充資訊**：注意事項、設計特點、備註等
- **潛在設計問題**：需求矛盾、不可行方案、遺漏的關鍵限制

### 3. 設計問題檢查（停止點）

在生成前，檢查以下潛在問題。若發現任何一項，**必須停止生成**並與使用者討論：

| 檢查項目 | 說明 |
|---------|------|
| 需求矛盾 | 功能 A 的規則與功能 B 的規則互相衝突 |
| 技術不可行 | 指定的技術方案明顯無法實現需求 |
| 關鍵遺漏 | 缺少讓系統正常運作的必要資訊（如：資料來源、權限） |
| 範圍模糊 | 核心功能的邊界不清晰，可能導致實作歧義 |
| 循環依賴 | 功能間存在循環依賴關係 |

**輸出格式**（當發現問題時）：

```markdown
## 🚨 設計議題討論

### 議題 1：[簡述問題]
- **涉及功能**：功能 X、功能 Y
- **問題描述**：[詳細說明矛盾/不可行之處]
- **建議方案**：
  - 方案 A：[說明]
  - 方案 B：[說明]
- **需要確認**：[具體要使用者回答的問題]
```

### 4. 生成正式 MVP 文件

確認無設計問題後，依據範本結構**就地修改**來源 MVP 文件。以下為各章節的生成規則：

#### 4.1 文件標頭（必填）

```markdown
# MVP-XXX: [功能標題]

**功能 ID**: MVP-XXX
**優先級**: [高/中/低]
**狀態**: 規劃中
**最後更新**: [YYYY-MM-DD]
```

- 功能 ID 和標題從檔案名稱推導
- 優先級若未指定，預設為「高」
- 狀態預設為「規劃中」
- 最後更新為當日日期

#### 4.2 需求概述（必填）

- 用 1-2 句話概括此 MVP 的整體目標與價值
- 若來源有「重要注意事項」或類似前置說明，以子章節形式保留

#### 4.3 主要需求 > 核心功能（必填）

- **完整保留**來源 MVP 的所有核心功能描述
- 正規化為統一的 Markdown 格式（編號清單 + 粗體功能名稱 + 縮排子項目）
- 不改寫語意，僅修正格式（如：修正縮排、統一標點符號）

#### 4.4 用戶故事（必填，由技能補充生成）

依據每項核心功能，生成對應的用戶故事：

```markdown
### [流水號]：[故事標題]

**身為** [角色]，**我想要** [目標行為]，**以便** [業務價值]。

**驗收標準**：
- [可測試的成功條件 1]
- [可測試的成功條件 2]
- ...
```

**生成規則**：
- 流水號格式為三位數：001、002、003...
- 驗收標準必須從核心功能描述中提取，**不可自行臆造**
- 驗收標準須為可測試的具體條件，避免模糊描述
- 若核心功能描述中有明確的業務規則（如限制條件、排除規則），必須全部列入驗收標準

#### 4.5 畫面操作流程（選填，依來源內容生成）

- 若來源有描述 UI 操作流程，正規化為流程圖格式（使用 `↓`、`├─`、`└─` 文字流程圖）
- 若來源未描述但核心功能涉及 UI 互動，依據核心功能推導基本操作流程
- 每個主要功能點至少一個操作流程

#### 4.6 外部資料來源（選填，依來源內容生成）

- 若來源有提及外部 API、資料源、第三方服務，以表格形式整理
- 若來源未提及則省略此章節

#### 4.7 建議 SPEC 切分（必填，由技能補充生成）

此章節為 MVP 需求文件的**最後一章**，目的是在 MVP 需求過大時，建議後續 SDD 階段的 SPEC 適合如何切分實現。

**編碼規則**：`SPEC-XXX-FeatureName` 的 `XXX` 必須繼承本文件 `MVP-XXX` 的編號。同一 MVP 拆成多份 SPEC 時，全部維持同一編號，以不同功能名稱區分；實作順序另列，不使用全域 SPEC 流水號或空號。例如 `MVP-005` 拆成 `SPEC-005-DocumentEditing` 與 `SPEC-005-StageDelivery`，不得把第二份編成 `SPEC-006-StageDelivery`。依賴引用使用完整 SPEC 名稱；BDD／TDD／風險文件後續沿用該完整名稱加上對應後綴。

**生成規則**：

1. 分析所有核心功能的**依賴關係**與**獨立性**
2. 依據以下原則建議 SPEC 切分：
   - **獨立性**：功能間無強依賴的，拆分為獨立 SPEC
   - **依賴順序**：存在前後依賴的功能，在 SPEC 描述中標註順序
   - **複雜度平衡**：單一 SPEC 不應包含過多功能，避免實作週期過長
   - **技術同質性**：技術面高度相關的功能可合併為同一 SPEC（如：共用資料模型的功能）
3. 每個建議 SPEC 需說明：
   - 包含的功能項目
   - 建議實作順序
   - 與其他 SPEC 的依賴關係

**輸出格式**：

```markdown
## 建議 SPEC 切分

基於核心功能的依賴關係與複雜度，建議後續 SDD 階段切分為以下 SPEC：

| 建議 SPEC | 包含功能 | 建議順序 | 依賴關係 | 說明 |
|-----------|---------|---------|---------|------|
| SPEC-XXX-[功能名稱A] | 功能1、功能2 | 第 1 順位 | 無 | [簡述切分理由] |
| SPEC-XXX-[功能名稱B] | 功能3 | 第 2 順位 | 依賴 SPEC-XXX-[功能名稱A] | [簡述切分理由] |
| SPEC-XXX-[功能名稱C] | 功能4、功能5 | 第 3 順位 | 依賴 SPEC-XXX-[功能名稱A] | [簡述切分理由] |
```

### 5. 使用者確認

將生成的正式 MVP 文件提交使用者確認，重點確認：

- 核心需求是否有遺漏或被改寫
- 用戶故事與驗收標準是否準確反映需求意圖
- 建議 SPEC 切分是否合理
- 是否有需要補充的額外資訊

交付前確認每個建議 SPEC 都繼承來源 MVP 編號，且完整名稱互不重複。既有歷史文件保留原名及來源關聯，不為套用新規則自動重編。

### 6. 完成 MVP 階段

使用者確認無誤後，準備進入 SDD 規格撰寫階段。
