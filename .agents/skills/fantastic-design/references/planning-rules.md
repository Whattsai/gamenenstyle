# 新 SD 流程的完整任務規劃規則

本文件定義 SD 流程的獨立規範。`fantastic-design` 用它規劃；`design-decision` 用它整合；`carefully-done` 用它執行與驗收。規劃並行條件不代表授權啟動代理；依使用者、工作區及執行環境的授權決定是否分工，單一代理也遵守同樣的責任與驗收要求。

## P1：完整流程基線

在寫入實作前建立同一份可觀察的完成契約，來源順序是使用者明確成果／範圍／限制、目標工作流的關卡與產物，再以本規則補足交付管理欄位；不得補造業務條件。fantastic-design 先將此契約寫入總覽與分項 SD，不另建平行計畫。

一次納入定位、各包 TDD、適用 UX、跨包整合、完整深度稽核、條件式補漏／重驗、證據與文件同步、最終交付。條件分支先寫觸發條件，實際發現後在同一基線填內容，不捏造缺陷、不每到一階段重開計畫。完整規劃不代表同時啟動所有階段。

## P2：完成契約與切包

每個成果記任務 ID、來源、交付物、可觀察驗收條件、驗證方式／證據位置、唯一執行責任、整合／驗收責任、依賴、狀態、排除範圍與不可執行檢查的原因／恢復條件。每項驗收都有負責者；不以最小管理要求新增業務功能。

先從 SPEC／BDD 的全部條件、操作、結果及畫面／狀態建立產品成果清冊，按現有業務責任、可交付功能與 UX 分解，先設計實際產品改動（含沿用、修改、新增、移除）、符號、契約、核心分支及資料流，再配置 TDD 驗證。禁止以測試層級／測試數量作為主要切包依據，禁止只將測試檔案當成業務實作成果。跨層行為指向全部實際改動及整合責任；純驗證、準備、稽核、交付或既有行為無須修改時，明列原因與實際產品位置。

按可交付、可指派、可驗證、可整合切包，避免同一交付物重複實作；為獨立審查而刻意重疊的唯讀檢查需說明效益。覆蓋所有來源及條件分支，不將整合和交付留成無主工作。

每包進一步依 [有序實作步驟契約](step-design.md) 細化至單一可觀察行為或可獨立檢查成果，寫足操作次序、檔案／符號、案例／斷言、命令／工作目錄、通過／停止條件及證據。每個 I 都有負責步驟，步驟引用原 I 而不另計進度；不能只用大型 Todo 或流程名稱充當執行設計。

## P3：寫入責任與共享資源

每包列精確可寫檔案／區段、排除範圍、輸入文件、契約版本、前置任務、起始條件、驗收及回傳格式（改動、檢查與結果、證據、假設、剩餘事項）。檢查全部受影響 repository／巢狀 repository 的既有改動，未釐清的重疊不得直接派寫。

共享 DTO、schema、生成檔、migration、fixture 與可變環境指定唯一寫入責任或隔離方式；不同原始碼檔案仍可能共用 DB、port、帳號或測試資料。安全並行必須同時滿足寫入不重疊、契約已定、依賴就緒、環境互斥或隔離、結果可整合；否則循序執行。責任移交前確認舊寫入者已停止或被隔離；新執行者沿用原 ID、有效成果與檢查點，不能兩者同時寫入。

有授權分工時，在總覽分項表記錄任務、責任人、實際指定的模型／effort（未知不捏造）、可寫資源、狀態、依賴／阻斷及驗證；對使用者提供相同資訊的簡潔進度視圖，在派出、停止、阻斷、恢復與驗收時更新。實際啟動成功才標為執行中。依能力、風險、協調與重工成本選最小有效分工；可用並行數是上限，不是必須用滿的目標。模型名稱本身不構成價格或節省的證據。主責人保留共同契約控制、整合監督與最終責任，子執行者發現越界要先回報，不自行擴張可寫範圍。

## P4：依賴、狀態與成本

列前置條件、共享契約版本、關鍵依賴鏈、阻塞完成的路徑、下一整合里程碑及安全起始條件。前置結果到位就檢查實際產物及證據，不必等不相關工作成批結束才開始後續。執行狀態與驗收狀態分離；工作者回報完成只表示可審查。

重大風險有負責者、觸發條件、處置／備援及時程／成本影響。遵守已給預算與期限，預留整合、驗證與可能修補；未知成本記定性估計或可觀察用時／重試，不編造金額、節省比例或硬期限。整合里程碑、重大阻斷或重複失敗時比較進展與成本，無新證據不重複同一失敗嘗試；先診斷再調整策略、降低並行或接手。資源限制不構成降低驗收標準的理由；超出明確限制或改範圍前先提出取捨。

## P5：變更、失效與恢復

記錄原設計、證據、影響、決策來源與版本變更；分析交付物、契約、來源文件、測試、責任、時程與成本。保持受影響工作停止，通知相關執行者；保存不受影響成果，受影響證據標為待重驗。已寫明設計要改由 carefully-done 的確認關卡處理，不能藉例行重構、環境修復或子技能自動補漏繞過。

在整合、重大變更、失敗策略調整或暫停前保存：已驗收與尚未驗收項、證據、目前執行者及可寫範圍／共享資源、剩餘依賴鏈、下一步、所需決策、恢復條件、需重驗成果及已知用時／不確定性。

中斷後先核對實際檔案、現況基準、證據與執行者狀態。使用者說已處理仍須查核外部條件；未滿足則保留 `Blocked`。條件解除後不重複請求同一授權；有代理時實際啟動可用原執行者續作並記錄結果，不以被動通知代替啟動。啟動失敗先確認不再寫入再接手／移交。持續追蹤至證據驗收，續作成功不是完成。無背景等待能力時保存檢查點、清楚交接，不宣稱自動恢復。對使用者所需決策集中說明原因、實際影響與操作，不讓多人重複詢問。

## P6：整合驗證、稽核與收尾

整合後在目前產物上實際執行必要的跨元件與回歸驗證；先前隔離環境通過不能直接當成整合成功。逐項查核斷言或功能操作是否證明來源條件，主責人檢視實際變更與結果，不只接受自述。只重驗因變更失效或尚未覆蓋的部分，不無因重跑昂貴檢查。

流程內稽核與全部任務之後的最終收尾分開：原定深度稽核、觸發修補、重驗及交付產物未完成前仍在執行階段。稽核可由適當負責者執行，不因名稱含稽核就預設只能由主代理做；最終整體責任與驗收決策由主責人承擔。

收尾逐項核對完成契約、目前版本、證據、文件同步及寫入者已停止，做必要最終整合檢查與小幅修補。只有具體缺陷、遺漏必要任務或新變更才在同一計畫重開受影響項；不因進入收尾再做一輪已有效完成的稽核。條件通過就交付，不無限追加一般複查。

## P7：不可降低的驗收標準

- `Verified`：目前可檢視證據已滿足驗收條件。
- `Accepted equivalent evidence`：已明確允許的替代證據證明同一驗收條件，記錄證據及使用者決策或工作流依據；可執行不代表等價。
- `Deferred`：必要外部條件不可用，記剩餘檢查、負責者（未知就明記未指派）與恢復條件，仍未驗收。
- `Incomplete`：缺實作／整合／驗證，或結果失敗／失效。

所有必要項目都是前兩種狀態、必要關卡成立且無違反驗收的缺陷才可報全部完成。缺 E2E 環境時 Unit／Integration 可記為已通過，但未證明同一條件的 E2E 仍為 `Deferred`。不得把列了命令、檔案存在、環境限制、AI 自評或工作者成功宣告當成通過。經明確核准刪除的範圍另記，不算作已驗證，也不能宣稱原範圍全部完成。
