# 有序實作步驟設計與執行契約

本規範由三個技能共同使用：`fantastic-design` 產生步驟，`design-decision` 重建整合後的步驟，`carefully-done` 依步驟執行與回填。步驟直接寫在每份分項 SD，不另建執行計畫或進度系統。

## 切分標準

每步只處理一個具體行為變更，或一項可獨立檢查的準備、整合、稽核、文件交付成果。完成時有可觀察結果，下一步不必猜測本步是否成立。適用的測試先行、實作與回歸放在同一步的子階段，不把只有 Red 成功誤當成產品已完成。

一個步驟若包含互不依賴的多個行為、不同前置／停止條件，或必須重新決定核心契約、演算法與失敗策略，就須先拆開或補齊設計。緊密相依、需一起驗證的跨檔案改動可放同一步，但逐一列出責任及驗證。切分不按固定檔案數、程式行數、時間或步驟數；不要求逐行指定程式碼。

「完成後端」「串接 API」「補測試」「依最佳實務處理錯誤」不足以作為步驟。要寫明本步負責的行為、具體輸入輸出、要改的符號、必要分支及可檢查的結果。

## 步驟身分、責任與計數

- 每步有穩定 ID，例如 `SD-001-S01`，以及一個唯一負責的 I 葉節點 ID；同一 I 可由多步共同完成。其他來源／Todo 可引用它，不複製同一工作。
- 設計檢查由既有 D 葉節點承擔，D 的完成條件包含其所管步驟設計完整。步驟本身沒有可計數 checkbox，不新增 D／I 分母，不另算步驟完成百分比。
- I 葉節點的必要步驟、該 I 的驗收條件及指定整合驗證全部有有效證據才可勾選。某一步通過或 Red 如期失敗都不代表 I 完成。
- 額外整合／稽核成果仍歸唯一負責的 I 葉節點；條件式修補先定觸發、責任與重驗範圍，不預造缺陷。實際發現後依核准設計補齊；需要新設計時先走確認關卡。

## 每步必填資訊

每份分項先列順序表，再按步驟重複完整區塊。可精確引用同一包已有定義，引用到欄位／ID；不得以泛指整份系統設計或其他候選代替執行內容。

| 欄位 | 足夠細緻的要求 |
|---|---|
| 成果與關聯 | 本步可觀察成果、唯一負責 I、來源 SPEC／BDD／TDD、檔案設計 F-ID、驗證 V-ID。 |
| 開始條件 | 前置步驟及其必要結果、跨包成果／契約版本、測試資料與環境；明列哪些驗證在後續整合步驟執行及其責任，不預設已通過。 |
| 必讀與可寫範圍 | repository、精確檔案與類別／函式／章節；相關規範／共享契約；可改區段、禁止改動及既有工作保護。行號可輔助定位，不能代替符號或章節。 |
| 行為與核心邏輯 | 輸入型別／格式、輸出、前後置條件、必要分支／演算法／狀態轉換、錯誤語意與副作用；交易、排序、冪等、重試及平台差異按適用性定案。 |
| 操作順序 | 本步內可執行的先後次序；適用時為 Red→Green→必要 Refactor→回歸。準備／整合／文件工作寫其適用檢查，不為了形式製造失敗。 |
| 案例與斷言 | 按來源需求給具體 fixture／輸入、預期值／狀態／錯誤及必要副作用斷言；列正常、錯誤、邊界的適用集合。不適用註明原因，不新增上游未確認行為。 |
| 命令與操作 | 每個子階段的工作目錄、命令／測試選擇器，或可重現的畫面操作；環境、資料建立及清理方式，變數的取得位置，不能填真實憑證或猜測工具命令。 |
| 結果判定 | Red 預期失敗的斷言或尚未建立的目標符號及原因；Green／回歸應通過的案例及結果。環境、無關編譯錯誤或執行錯案例，不得當成預期 Red；缺目標符號的編譯失敗僅在設計已明列該符號與原因時才成立。 |
| 停止與下一步 | 哪些缺項、失敗或現況差異必須停止；哪些可在核准範圍修正；下一步 ID 及其可開始條件，沒有後續就寫明本步交付責任。 |
| 證據與恢復 | 結果回填位置、實際狀態／子階段、命令與目前版本、測試／程式位置、待重驗、已發生副作用與資料清理現況；恢復先查實際成果，避免重複執行。 |

測試資料可採明確的代表值搭配參數表／生成規則，不必窮舉無限輸入。已確認門檻的邊界要列門檻兩側與臨界值。時間、亂數及外部呼叫需說明控制方式或實際驗證條件；不能用 mock 通過代替已要求的真實平台／整合驗證。

## 順序與執行關卡

順序表必須無循環、無缺失的步驟引用，包含適用的測試、實作、UX、整合、稽核與文件同步。每個實際改動檔案均有負責步驟；每個 I 均有必要步驟及其驗收依據，不能只將流程名稱列在總覽。

開始前檢查具體條件；一次執行目前步驟並在各子階段記錄實際結果。只有本步規定的通過條件成立，依賴它的下一步才可開始。後續專屬的整合檢查可按已核准依賴安排在後面，但不得提前勾選要求該檢查的 I 或來源項目。

測試失敗且設計未變時，可在本步既定可寫範圍及邏輯內診斷修正，重驗受影響項；不能任意改斷言、降門檻、跳測試或反覆盲目重試。前置或必要環境缺少時記原因與恢復條件；已寫明的行為、檔案、契約、依賴、步驟順序或驗證方式需改時，停止本需求後續實作並走既有設計變更確認。

在完成前置準備與全包設計閱讀後，後續以當前步驟、相關來源、前置成果與共享契約作工作焦點；遇到跨包影響須回讀受影響內容，不能只靠簡化摘要。步驟不得豁免工作區指示或擴大寫入／外部操作授權。

## 設計交付前檢查

逐步模擬執行者從既定基準開始能否找到輸入、定位檔案、完成操作、判定結果並選擇下一步，不執行產品修改。若還需要自行猜測測試值、核心分支、資料權威、工作目錄或失敗處置，先補設計再交付。桌面檢查不等於產品實測。

確認步驟與逐檔案設計、測試表、I 葉節點及矩陣互相對得上。整合 final 時重建順序與 ID 對照，確認候選合併沒有遺漏前置或重複寫入；不直接拼接不同候選的順序表。
