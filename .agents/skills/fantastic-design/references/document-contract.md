# SD 文件、基準與進度契約

本契約由三個新技能共同使用，版本為 `SD-contract-v2`。它不修改既有 SDD／BDD／TDD 格式、交接與計數方式。

v2 要求每份分項具備有序實作步驟，依 [步驟設計契約](step-design.md) 產出與執行。既有 v1 包保留成果及版本；接手時若缺必要步驟，先補齊設計、依既有確認規則更新核准，再續作，不得只改契約版號或推定新增內容已核准。

## 文件配置與身分

由來源 SPEC 實際所屬的文件根目錄推導 `docs/`，包括已歸檔 SPEC 的來源關聯；無法唯一判斷時詢問，不猜 repository 根目錄。以下 `SPEC-XXX-FeatureName` 指完整檔名主幹：

```text
docs/sd/SPEC-XXX-FeatureName/
├─ candidates/<AI與模型標識>/<設計批次>/
│  ├─ 00-overview.md
│  ├─ 01-system-design.md
│  ├─ 02-traceability.md
│  └─ plans/SD-NNN-功能名稱.md
└─ final/
   ├─ 00-overview.md
   ├─ 01-system-design.md
   ├─ 02-traceability.md
   ├─ 03-design-decision.md
   └─ plans/SD-NNN-功能名稱.md
```

- 完整 SPEC 名稱加上來源 MVP／SPEC 路徑共同識別文件包。同編號不同功能不混放、不相互取代。
- AI／模型只記實際可取得資訊，分別記錄取得依據；未知寫「未提供」，目錄可用 `ai-unprovided-model-unprovided`。目錄標識採適用平台的合法字元，原始資訊留在 metadata。
- 每次新設計使用新批次，例如時間加序號；先查碰撞，同模型重新設計也不得覆寫舊批次。包內修訂以遞增設計版本追蹤。
- 候選計數以完整設計批次為單位，與 `plans/` 檔案數無關。只排除明確記有被誰取代、日期、原因及替代包連結的批次；不以時間較舊或未核准為由排除。發現不完整批次先揭露並補齊或取得明確處置，不以忽略它來自動套用唯一候選規則。
- 歷史批次保留。重新建立 final 前保存舊 final 的完整內容至新的歷史候選批次並標記已取代、原路徑與原版本，才更新固定 `final/`；不得讓核准過的設計只剩被覆寫的檔案。

## 來源、程式與設計版本

每包總覽記錄來源文件清單與各自版本或 SHA-256、確認紀錄、工作區路徑／commit、相關 staged／unstaged／untracked 檔案及內容摘要／指紋。每份 SD 記錄包身分、版本、來源及設計基準的引用。不能以同一 commit 代表工作樹內容相同。

設計版本與進度更新分開：總覽列出設計版本、設計內容清單及核准邊界；該清單至少涵蓋系統設計、追溯中來源／責任／驗證安排、每份分項的行為、檔案、邏輯、契約、依賴、驗證、Todo 定義，以及步驟順序、案例／斷言、通過／停止條件。核准紀錄必須能還原當時內容，可用 Git commit 加工作樹差異快照，或保存設計欄位的內容快照／雜湊及可取回的副本。僅有無法取回內容的雜湊或版本字串不足以確認核准範圍。

一般執行狀態、時間、結果、完成 checkbox 及證據回填不改設計版本。更動已記載的設計內容須遞增版本並列影響，不得以「只是回填」掩飾設計改動。未受設計限制且不影響核心設計的局部選擇不用升版。

恢復或開工時比較來源、程式、設計核准快照與現況。預定的實作改動可藉檢查點與證據識別；其他漂移須分析影響。無影響者記錄理由，有影響者標記核准／證據失效、停止依賴工作並走確認，不自動替使用者重新核准。

## 三種進度與唯一計數

每份分項的「實現檢查清單／Todo」是唯一 SD 計數來源；每個葉節點有穩定 ID、`D`（設計）或 `I`（實作驗證）類型、唯一分組、來源、責任與驗收／證據欄。摘要、里程碑、矩陣引用、父項與檢查點不再建立可計數副本。新增／移除葉節點定義屬設計範圍變更，不能藉此調整分母湊完成。

每個實作步驟有穩定 S-ID 及唯一負責的 I-ID；步驟只記執行狀態與證據，不增加 checkbox、完成數或分母。多步共同負責一個 I 時，全部必要步驟、I 驗收及指定整合驗證成立才可勾選該 I；不依步驟完成比例給部分完成分數。原 D 的設計完成條件包含其相關步驟設計完整性。

1. **設計完成度**：`D 已完成葉節點 / 全部必要 D 葉節點 × 100`；必須已具體寫入設計並通過一致性檢查才算完成。人工核准是獨立關卡，不由百分比推定。
2. **BDD／TDD 設計涵蓋率**：由追溯矩陣分別計算「已有完整 SD 設計、責任、檔案與驗證安排的唯一來源項目數 / 全部來源項目數」。SPEC 涵蓋也逐項查核。這是涵蓋率而不是完成 checkbox；跨包來源只有全部設計到位才算涵蓋。
3. **實作驗證完成度**：`I 已取得有效驗收證據的葉節點 / 全部必要 I 葉節點 × 100`。`Verified`、有明確允許且證明同一條件的 `Accepted equivalent evidence` 才可勾選；`Deferred`／`Incomplete` 不算完成。

百分比四捨五入到一位小數；零分母記 `N/A（0/0，原因）`，不能顯示 100%。進度條與完成數同步，總覽以各分項分子／分母相加再算，不平均百分比。分層／分組只計各自葉節點，子分組與父摘要不重複加總。

來源 BDD／TDD 照既有項目與慣例分別計算，不用 SD 葉節點數替代。跨包 Scenario／測試要在所有必要 I 成果及整合驗證成立後才可勾選；矩陣指明整合驗證負責包。既有完成成果先查核證據與現況，保留有效部分，不因建立 SD 歸零；無法追溯或因變更失效的完成項才退回待驗證並說明原因。

## 實作、BDD 與畫面涵蓋判定

完整設計涵蓋須同時具備來源行為（BDD 每個條件、觸發、結果及 Examples）、實際產品檔案／符號與核心實作（新增、修改、移除或證實沿用）、適用畫面與元件／互動／狀態／平台、必要跨包 F／S／I、驗證 V 及證據安排。TDD ID 或測試位置映射只是結構追溯，不計完整設計涵蓋。純驗證或無 UI 依適用性說明並提供被驗證的產品位置或不適用理由。總覽分別揭露結構映射與完整設計涵蓋，畫面／行為清冊只作設計稽核，不新增 D／I 或來源計數分母。缺任一必要欄位保留 Draft，不能核准或開工；既有包不自動失效，但接手時依原基準查核缺項，涉及補改設計按既有版本及核准規則辦理。本段為 v2 既有完整設計標準的明確化，不變更固定計數與核准契約。

## 狀態與人工確認

執行狀態可用 `Planned`、`Running`、`Ready for review`、`Accepted`、`Blocked`；驗收另記 `Verified`、`Accepted equivalent evidence`、`Deferred`、`Incomplete`。執行結束、代理回報或「程式存在」不是驗收通過。

SD 交接狀態：

- `Draft`：設計未完整。
- `Awaiting approval`：設計稽核通過，等待指定包與版本的明確核准。
- `Ready for carefully-done`：來源交接有效、設計完整且逐項涵蓋、無未解除阻斷，並有該包具體設計版本的使用者確認及核准快照。
- `Blocked`：前置、核准、基準或設計變更關卡未滿足；記原因與恢復條件。

核准記錄使用者原意／可追溯對話位置、日期、包路徑、版本、核准邊界與快照。已有有效明確確認就回填紀錄，不重複詢問；「開始開發」不替代尚未選定或不可識別設計的核准。候選核准不轉移到整合後 final。使用者沉默、經過時間、AI 自評 100% 都不是核准。

`Ready for well-done` 仍留在 TDD；`Ready for carefully-done` 只在 SD 交接。readyforwelldone、可進行 carefullydone 是交接狀態，沒有同名新技能。
