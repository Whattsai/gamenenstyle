# Fantastic Design

此技能從資深系統設計角度把已確認需求轉成可實作、可驗證的完整設計，不修改產品程式、測試、設定或基礎設施。

## 核心規則

1. 先讀目標範圍的 `AGENTS.md` 或同等 agent 指示、README、分析／設計／開發方法文件。涉及其他工作區、服務、資料庫或模組時，也先讀其指示、README、相關文件及實際程式碼。
2. 使用使用者指定或 TDD 規劃交接列出的 MVP、完整名稱 SPEC、BDD、TDD；不得只憑共用的 `SPEC-XXX` 判定關聯。
3. 開始時必讀本技能的 [文件與進度契約](references/document-contract.md) 和 [完整任務規劃規則](references/planning-rules.md)，依其中的獨立規範完成設計與交接。
4. 必須依四份指定範本產出，不得改成一般工作包格式；每份分項都保留完整設計與進度結構，不適用章節保留並說明原因。
5. 遵循工作區語言、命名與文件管理慣例；無慣例時沿用使用者語言。路徑、API、類別及函式名稱保留原文。
6. 不把設計涵蓋率當成實作完成度，不因新增 SD 重設有效的既有完成項目，不自行核准需求或設計。

## 前置條件與交接檢查

逐項查核並在 SD 總覽留下結果：

- 來源 MVP、SPEC、BDD、TDD 可讀，SPEC 與風險已取得使用者確認。
- TDD 規劃交接狀態為 `Ready for well-done`，文件包路徑正確。
- 已持久化風險各有使用者決策、回寫位置或接受原因；缺漏已補回正確上游文件，不只留在交接摘要。
- 注意事項已讀；沒有 `Blocked`、待確認風險或未解除阻斷。
- 已檢查現行程式、測試、實際 build/test/lint 命令、資料庫、前端、部署環境與工作樹改動，包括受影響的巢狀 repository。

缺少必要前置時，記錄缺項、影響與恢復條件，停止依賴它的設計並通知使用者。不得搬用 `well-done` 的持續開發或自行降級規則製造核准、繞過阻斷。此處檢查原有交接，不改寫 `Ready for well-done` 的意義。

## 自主作業與確認邊界

在既有授權內自行完成研究、SD 撰寫、一致性稽核與 SD 缺漏修正。

發現上游需求衝突或缺漏時，先保存原文、現況證據、實際功能影響、白話案例、建議修改、替代方案及受影響的 SPEC／BDD／TDD／SD。取得針對該內容的明確確認後，才修改必要上游文件；更新來源基準並重查追溯及交接條件。一般設計工作不構成修改上游需求的授權。

## Phase 1：定位與建立批次

1. 完成前置檢查，確認本輪唯一完整 SPEC 與來源文件根目錄；不在 repository 根目錄任意建立 `docs/`。
2. 依文件契約建立 `docs/sd/<SPEC 完整名稱>/candidates/<AI與模型標識>/<新設計批次>/`。保留所有歷史批次；未知模型記為未提供。
3. 記錄來源版本／雜湊、程式碼 commit、相關 staged／unstaged／untracked 改動及目前有效成果；不覆寫使用者工作。

## Phase 2：系統設計

依 [系統設計範本](assets/01-system-design.template.md) 從已確認需求與實際程式填寫：現況／目標架構、模組責任、分層與依賴方向、同步／非同步資料流；DDD 通用語言、業務邊界、Aggregate、不變條件、資料權威與跨業務互動；已確認變動方向、擴充點與函式共用界線，避免錯誤共用與過早抽象。

具體決定執行平台、儲存／快取／訊息／網路／外部服務、容量與成本限制；必要框架核心、重要函式輸入輸出、演算法、狀態轉換、交易、併發與冪等；API／DTO／schema、驗證與錯誤語意、相容性／版本、遷移與回復；安全、權限、隱私、韌性、效能、可觀測性、可測試性、部署，以及前端頁面／元件責任、Loading／空／錯誤狀態、導覽與平台差異。

用流程圖、狀態圖、決策表、介面或偽碼補足必要核心邏輯，讓實作者不必重新決定核心架構。逐項說明沿用、調整、新增的理由與回歸影響，只做必要且最小改動；局部命名等未限定且不影響設計的選擇留給實作。

## Phase 3：分項規劃

**實作設計優先（強制）**：先依 SPEC 與 BDD 的 Given／When／Then／And／But（含 Examples、角色、正常／替代／錯誤／邊界及非功能條件）盤點實際產品行為，再由現行產品程式及架構找出缺口，按可交付功能、畫面／互動與業務責任切包，先定實作檔案／符號、核心邏輯與跨層資料流，再將 TDD 映射為驗證。不得按 TDD 測試名稱、層級或數量主導切包，亦不得以測試檔案修改代替實作設計。已存在且不需修改的產品行為須列實際程式位置、沿用理由及驗證，不強制虛增改動。純驗證／稽核／文件／準備步驟可不改產品，但須說明原因並指向其驗證的產品成果。

**畫面設計（適用時強制）**：先全量盤點 BDD 及 SPEC 的畫面、角色／權限、導覽、互動與平台。按頁面、區域、共用元件、互動行為及狀態責任拆成可執行 SD；逐一設計布局／層級、內容與素材、操作／手勢、可用／禁用／Loading／空／錯誤／重試、焦點／返回、API／DTO／事件及本地與權威狀態同步、平台差異與必要視覺驗證。採用既有畫風及元件契約；需要新素材時列來源、格式、尺寸、資產路徑與驗收，不擅改已確認 UX。所有適用畫面及 Scenario 的行為必須映射至實際 UI 檔案／元件／handler／狀態與步驟，不能只映射 E2E。沒有 UI 的需求明記證據及不適用理由。 設計時查閱適用的 `bdd-frontend-ux-implementation` 規則，將 SPEC 與 BDD 前端需求交叉比對納入 SD；不執行其開發、進度回寫或核准流程。遇到上游缺漏依本技能確認邊界處理。

依規劃規則一次納入 TDD、適用 UX、整合、深度稽核、條件式補漏／重驗及交付，按可交付、可指派、可驗證、可整合單位建立多份 `plans/SD-NNN-功能名稱.md`，不按固定檔案數切包。

每份必須套用 [分項實作設計範本](assets/SD-plan.template.md)，逐一列出實作、測試、設定、migration、基礎設施與必要文件的精確改動路徑、位置、核心邏輯、白話理由、契約、責任、可寫範圍、依賴、驗證與證據位置。共用檔案只有一個寫入責任；其他分項引用該成果而不重複實作。

必讀 [有序實作步驟契約](references/step-design.md)，在每份分項內將 I 葉節點細化為有穩定 ID 的步驟。逐步寫明成果、前置、必讀與可寫檔案／符號、核心分支、具體案例／斷言、工作目錄／命令、通過與停止條件、下一步及恢復資訊。每個 I 都有全部必要步驟；步驟不另計進度，不把整份 SD 或大型 Todo 當成一次執行單位。

## Phase 4：逐項設計稽核

套用 [追溯矩陣範本](assets/02-traceability.template.md)，逐項串接 `MVP／SPEC → BDD → TDD → SD → 實作／測試檔案 → 驗收證據`，包含錯誤、邊界、替代流程及非功能需求；不得抽樣或只核對數量。

確認所有 SPEC、BDD、TDD 項目有具體可執行設計、唯一責任及驗證安排；逐一核對 BDD 條件、觸發、每個結果及畫面行為的產品實作位置、F／S／I 與 V 映射。只列 ID、測試名稱、測試檔案、泛指產品模組或缺少核心邏輯不計完整設計涵蓋，D 不得勾選；即使所有 TDD 已映射也保持 Draft。跨包項目列出全部必要成果及整合驗證。設計階段的產品實作證據待回填；已有有效證據可引用並標明查核結果。

依步驟契約逐步桌面檢查，從實際基準確認執行者能定位檔案、取得輸入、按序操作、判定結果及選擇下一步；逐一核對 I／步驟／F-ID／V-ID，檢查依賴無循環、無遺漏及重複工作。仍需猜測核心分支、案例、命令或失敗處置時先補設計，不標記可交接。

## Phase 5：修正循環

修正 SD 內的缺漏，重查受影響契約、資料流、依賴、檔案責任與覆蓋率。上游問題走人工確認；不得為湊 100% 刪除來源項目或降低驗收標準。必要前置未成立時保存檢查點與待決策事項。

## Phase 6：設計交付

依 [總覽範本](assets/00-overview.template.md) 彙整實際進度、來源／程式基準、分項清單、逐項涵蓋結果、風險與待確認項。交付完整候選文件包路徑及具體設計版本，停止等待人工確認，不開始開發。

未核准時 SD 交接為 `Awaiting approval`；已有對同一文件包及有效設計版本的明確確認才可記錄 `Ready for carefully-done`。此狀態只寫入 SD 交接，不取代 TDD 的原規劃交接。多候選可選擇使用 `design-decision`，不是必要步驟。

## 驗證與維護

交付前核對範本結構、所有來源項目、相對連結、版本、責任邊界、三種進度及人工確認紀錄；至少執行 `git diff --check`。不把設計推演宣稱為產品驗證。

維護本技能時使用 [能力完整性檢查](references/capability-checklist.md) 與 [情境檢查](references/scenario-checks.md)；日常設計執行不必讀取這兩份維護資料。規則修訂時同步更新相關流程、範本及情境檢查。
