# 執行紀錄與情境檢查

本文件支援 `mighty-pm` 的分工、交接與驗收。依任務規模選用欄位，優先併入目標流程既有的任務或交接文件；不要另建內容相同的第二份計畫。一般短任務不必填寫完整表格。

## 完成契約與執行紀錄

記錄使用者要求的成果、範圍邊界、來源文件、有效授權與必要關卡。已有時程或預算限制時一併記錄；未提供時不捏造金額或期限。

| 任務 ID | 來源需求 | 交付物與驗收條件 | 執行者／可寫範圍 | 依賴／契約版本 | 狀態／證據 |
|---|---|---|---|---|---|

任務執行狀態可使用 `Planned`、`Running`、`Ready for review`、`Accepted`、`Blocked`，但不能直接將執行狀態換算成驗收通過。最終驗收須另依主技能的 `Verified`、`Accepted equivalent evidence`、`Deferred`、`Incomplete` 判定。

實質風險需記錄負責人、觸發條件與處理方式。例如：共用測試 DB 的重置會影響另一組測試，由 PM 排定互斥使用，或先建立隔離環境。

### 完整工作流程的規劃邊界

以 `$mighty-pm (well-done xxx)` 為例，括號內是一次納入初始計畫的完整範疇。括號僅用來表達分組，呼叫時不強制使用。

| 初始計畫涵蓋的工作 | 分工與依賴 |
|---|---|
| 前置定位、文件包與關卡檢查 | 依目標技能及既有授權決定可開始的工作。 |
| TDD 開發與適用的 Frontend UX 實作 | 依寫入範圍、契約、成本及依賴分工。 |
| SPEC／BDD／實作深度稽核 | 可規劃為子代理任務；須在所需實作與證據就緒後，依技能逐項審核。 |
| 稽核觸發的補實作與再次稽核 | 初始計畫先列條件分支；實際缺漏出現後補入內容並執行，仍屬原範疇。 |
| 流程要求的文件、驗收證據與交付產物 | 納入初始計畫並明確指派；全部就緒才可進入 PM 收尾。 |

主代理全程承擔責任，但「流程內的稽核任務」與「全部任務完成後的 PM 收尾」是不同層次。不能因某階段名稱包含稽核或驗收，就強制改由主代理執行。一次完整規劃仍需遵守階段先後，不代表全部任務同時派出。

## 工作者交接內容

派工訊息應足以讓工作者在不猜測業務規則的情況下執行：

- 任務 ID、來源需求、必要的 `AGENTS.md`／Skill 與參考文件。
- 預期產物、允許修改的檔案／資源、明確排除範圍。
- 前置任務、可開始條件、使用的 API／DTO／schema 契約版本。
- 驗收條件、要執行的檢查、共享資源的使用時段或隔離方式。
- 遇到範圍重疊、契約變動或缺少決策時的回報條件。
- 回報修改清單、驗證命令與結果、證據位置、假設及未解事項。

主代理保留最終責任。工作者可指出建議修改的共用檔案，但不能因此取得其寫入權。

## 檢查點與恢復

在整合里程碑、重大變更、失敗策略調整或暫停前，更新以下資訊：

- 已驗收項目及其證據；尚未驗收項目與原因。
- 正在執行的工作者、寫入範圍、共享資源使用情況。
- 影響完成時間的依賴鏈、下一個里程碑及可執行的下一步。
- 決策來源、受影響契約版本、需要重驗的成果。
- 已知的時間／用量、估計的不確定性、重試原因與調整後策略。

恢復工作時先核對實際檔案、測試證據與工作者狀態；不能只依紀錄重新派出同一份工作。

### 子代理停止與續作紀錄

遇到未完成就停止的工作者，在同一份執行紀錄補上：

| 任務 ID／工作者 ID | 停止原因／目前狀態 | 已完成成果／剩餘工作 | 所需決策或操作／恢復條件 | 使用者回覆或查核證據 | 續派對象／結果／下一步 |
|---|---|---|---|---|---|

PM 統一向使用者說明需要介入的原因與具體操作；已有的授權不重複詢問。條件解除後，優先對仍可用的原子代理實際送出續作任務，記錄啟動結果，再持續追蹤至驗收。若原子代理失效，先確認其不再寫入，再由替代工作者或 PM 依同一任務 ID 接手。

`Blocked` 表示仍有未解除條件；確認已啟動續作後才標記 `Running`。阻塞解除、續派成功、交付物驗收通過是三個不同事件，應各自留下證據。若執行環境無法持續等待，保存紀錄並請使用者完成操作後回覆，不宣稱已在背景自動恢復。

## 驗收紀錄

| 驗收項目 | 當前產物／版本 | 檢查與實際結果 | 證據位置 | 驗收狀態 | 替代依據或待辦條件 |
|---|---|---|---|---|---|

缺少 E2E 執行環境時，可以記錄已通過的 Unit／Integration 檢查，但若它們未證明同一個驗收條件，E2E 項目仍是 `Deferred`。環境限制、子代理自述成功或測試指令列出而未執行，都不是通過證據。

### 主代理收尾

完整目標流程內的所有適用任務，包括原定稽核、已觸發的修補與重驗、必要交付產物，皆完成且證據經檢視後，才進入 PM 收尾。此時由主代理直接確認整體成果與證據一致性、完成必要的最終檢查與文件彙整，並作最終交付；不因進入收尾就重做已有效完成的深度稽核。

若原定稽核或修補尚未完成，仍屬流程執行階段。若收尾才發現具體缺陷或漏列必要任務，應在同一計畫重新開啟受影響項目；小幅問題由主代理修正，較大且可隔離的工作可記錄效益與範圍後委派。完成並重新驗證後再回到收尾，不重新開啟整套計畫或重複一般稽核。

## 維護技能時的情境檢查

這些情境用來檢查調度決策與驗收判定，不是一般任務每次都要執行的額外流程。桌面推演與實際多代理測試應分別記錄，不得將推演宣稱為實測。

| 情境 | 應觀察到的行為 |
|---|---|
| 目標 skill 未提並行，存在兩個獨立且值得委派的任務 | 在環境允許時分工，仍維持目標 skill 的階段與關卡。 |
| 任務很小，派工與交接成本高於直接完成 | 主代理自行處理，保留必要驗證。 |
| API、App、Management 寫入不同檔案，但共用 DTO 與測試 DB | 明確分配 DTO 寫入者；DB 測試採互斥排程或隔離，不因檔案不同就認定完全獨立。 |
| 工作者要求改變 DTO nullability | 先確認來源需求與影響，更新契約、通知使用端，重驗受影響成果。 |
| 使用者已有未提交的 UI 修改 | 辨識並保護既有內容；未釐清的重疊寫入不得直接派工。 |
| 較便宜的工作者重複失敗，沒有新增證據 | 重新診斷、調整策略或由主代理接手，不無限重試或直接降低驗收要求。 |
| 工作者回報完成，但必要 E2E 無法執行 | 記錄已驗證部分；無有效等價證據時保留 `Deferred`，不得宣稱全部完成。 |
| 前置關卡要求確認，另有概括性的「持續執行」指示 | 依指示優先序、特定前置條件及既有授權處理；缺少必要決策時只保留不依賴該決策的工作。 |
| 沒有專用 skill，使用者只要求診斷原因 | 以診斷結果和證據建立完成契約；不自行擴張成修復或部署。 |
| 子代理不可用，或任務中途恢復 | 主代理承接可行工作；恢復時核對現況，避免重複執行或兩個工作者同時持有寫入權。 |
| 工作者因需要使用者操作而停止 | PM 保存檢查點並統一通知所需操作與恢復條件，繼續不受影響的任務。 |
| 使用者完成操作並回覆，原子代理仍可用 | PM 查核條件後實際啟動原子代理續作，提供更新資訊並追蹤至驗收，不重複要求相同授權。 |
| 使用者回覆已處理，但檢查仍顯示必要條件未滿足 | 保留受影響任務的 `Blocked` 狀態，說明缺少的證據或操作，不直接續派。 |
| 恢復條件已滿足，但原子代理續作失敗 | 確認原工作者不再寫入後，將同一任務及有效成果交給替代工作者或 PM；不能只記錄「已通知」就結束。 |
| 子代理已續作，但尚未交付驗收證據 | 維持追蹤；續作成功不能計為任務完成。 |
| 原定任務含深度稽核、修補循環與交付產物，全部完成且證據有效 | 主代理直接完成整體確認與收尾，不再建立一輪收尾子代理或重做相同稽核。 |
| 必要驗證均已通過，沒有新變更或具體未解問題 | 主代理完成紀錄與交付，不追加一般複查或重複稽核。 |
| 收尾才發現具體、工作量較大且可隔離的缺口，或初始計畫漏列必要審查 | 在同一計畫重開受影響工作，必要時委派；完成並重驗後再由主代理收尾。 |
| 一開始規劃 `well-done`，其中包含 Phase 4 深度稽核 | 將稽核及其前置依賴列入完整計畫，可指派子代理；不將它提前歸類為 PM 收尾。 |
| 實作已完成，但原定稽核未開始，或稽核發現的缺漏尚未補齊 | 保持流程執行狀態，依原計畫執行稽核／補實作／重驗，尚未進入 PM 收尾。 |

若做獨立演練，只提供情境輸入與技能，不先提供上表的預期答案；再以可觀察的分工、變更處理及驗收結果評估。

## 專業依據與採用範圍

- [APM：Project manager 職能](https://www.apm.org.uk/jobs-and-careers/career-path/what-does-a-project-manager-do/)：範圍、時程、成本、風險、品質、資源及成果責任。
- [PMI：專案計畫的組成](https://www.pmi.org/learning/library/project-plan-assembly-elements-summary-3128)：交付物、責任、驗收、里程碑、資源預估及變更管理。
- [APM：變更控制](https://www.apm.org.uk/resources/what-is-project-management/what-is-change-control/)：記錄變更、評估影響、依權限決策並更新計畫。

工作者寫入範圍、契約版本、模型選擇與驗收狀態是上述職能在 AI 協作上的實作設計，不代表專業組織規定的工具或認證標準。
