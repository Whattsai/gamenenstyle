# 實作前風險與缺漏稽核技能

此技能用於「BDD/TDD 文件生成後、TDD 開發前」的深度預審，目標是在寫程式碼之前就識別出潛在問題、技術風險和測試缺漏，避免開發中才發現需要大幅調整。

## 何時使用

- 使用者確認 SPEC、BDD Feature、TDD 測試清單後，準備進入 TDD 開發之前
- 使用者要求「實作前評估」、「風險分析」、「檢查缺漏」
- 需要深入評估規格文件與 TDD 清單的完整性和可行性
- 使用者提到「開始開發前先檢查一下」

## 核心原則（務必遵守）

1. **全面審查，不得省略**：MVP 需求、SPEC 規格、BDD 場景、TDD 測試清單都要逐項檢視。
2. **問題必須具體**：每個風險/缺漏必須指出「在哪個文件、哪個章節/場景/測試」有問題。
3. **解決方案必須可執行**：不能只說「需要注意」，必須提出具體的解決方案或補強測試。
4. **與使用者討論**：風險評估結果必須清楚呈現；需要使用者確認的問題必須先說明實際功能、營運或資料面的影響，等待使用者確認後才修改 TDD 文件。
5. **補齊而非重寫**：將缺漏項目新增到現有 TDD 文件中，不重新生成整份文件。

## 必要輸入文件

| 文件 | 路徑模式 | 用途 |
|------|---------|------|
| MVP 需求 | `docs/requirements/MVP-XXX-*.md` | 原始需求與範圍界定 |
| SPEC 規格 | `docs/specs/SPEC-XXX-*.md` | 功能設計與技術規格 |
| BDD 場景文件 | `docs/bdd/SPEC-XXX-*-BDD.md` | 行為場景描述 |
| TDD 測試清單 | `docs/tdd/SPEC-XXX-*-TDD.md` | 待執行的測試項目 |

> 備註：新 BDD 產出以 Markdown `-BDD.md` 為標準；若舊專案已存在歷史 `.feature` 檔案，仍依實際檔名讀取，不重新命名既有檔案。

上述模式只供探索；實際稽核與回寫必須鎖定完整的 `SPEC-XXX-FeatureName` 文件包及其明確關聯的 MVP。新 SPEC 的 `XXX` 繼承來源 MVP 編號，同一 MVP 的其他 SPEC 具有不同 `FeatureName`，不得僅按數字配對或混算進度。若另外保存風險報告，使用 `SPEC-XXX-FeatureName-RiskAudit.md`，沿用本份 SPEC 的完整主幹，不重新配號。歷史文件依實際名稱與來源連結讀取，不自動重編。

## 執行流程

### Phase 1：文件讀取與需求對照

#### 1.1 載入所有文件

依序讀取 MVP 需求 → SPEC 規格 → BDD Feature → TDD 測試清單，建立完整理解。

#### 1.2 需求追溯矩陣

建立以下對照關係，確認每個需求都有對應的場景與測試：

```
MVP 需求項目 → SPEC 功能需求 → BDD Scenario → TDD 測試案例
```

**檢查重點**：
- MVP 中的需求是否都反映到 SPEC 中
- SPEC 中的功能需求是否都有 BDD 場景覆蓋
- BDD 場景是否都有對應 TDD 測試案例
- 是否有 TDD 測試案例找不到對應的 BDD 場景（孤立測試）

### Phase 2：技術風險深度評估

針對 SPEC 定義的技術架構與實作方式，逐一評估以下面向：

#### 2.1 架構與設計風險

- [ ] Domain Model 設計是否合理（實體邊界、聚合根、值對象）
- [ ] 層級間依賴是否符合 Clean Architecture 原則
- [ ] 介面設計是否足夠（Repository Interface、Service Interface）
- [ ] DTO 與 Domain Entity 的映射是否完整

#### 2.2 技術可行性風險

- [ ] 外部 API/服務整合是否有 Mock 方案
- [ ] 資料儲存方案是否明確（DB/JSON/記憶體）
- [ ] 非同步操作的錯誤處理是否完善
- [ ] 並發/競態條件是否需要考慮
- [ ] 效能瓶頸是否已識別（大量資料、網路延遲）

#### 2.3 邊界條件與例外處理

- [ ] 空值/null 處理是否涵蓋
- [ ] 無效輸入的驗證是否充分
- [ ] 超出範圍的數值處理
- [ ] 字串長度/格式限制
- [ ] 權限與授權檢查

#### 2.4 整合點風險

- [ ] 前後端 API 契約是否對齊
- [ ] 跨模組/跨服務的資料一致性
- [ ] 第三方服務失敗時的降級策略
- [ ] 配置檔案/環境變數的依賴

### Phase 3：TDD 測試清單完整性稽核

#### 3.1 測試層級覆蓋檢查

逐層檢查 TDD 測試清單：

**單元測試層**：
- 每個 Domain Entity 的建構、驗證、業務邏輯是否都有測試
- 每個 Application Service 的方法是否都有測試
- 是否涵蓋正常路徑 + 異常路徑

**集成測試層**：
- Repository 的 CRUD 操作是否都有測試
- 跨服務協作流程是否有測試
- 資料持久化與讀取是否有測試

**API 測試層**：
- 每個 API 端點是否都有測試（含各種 HTTP 狀態碼）
- Request/Response 格式驗證
- 認證/授權場景（如適用）

**E2E 測試層**：
- 核心使用者流程是否有端到端覆蓋
- 前端互動到後端資料持久化的完整鏈路

#### 3.2 BDD 場景 → TDD 逐項映射

對每個 BDD Scenario，確認：

| 檢查項目 | 說明 |
|---------|------|
| Happy Path 測試 | 正常流程的每個 Then 斷言是否有對應測試 |
| Alternative Path 測試 | 替代流程是否有測試覆蓋 |
| Error Path 測試 | 錯誤場景的每個錯誤訊息是否有測試驗證 |
| Edge Case 測試 | 邊界條件是否有測試覆蓋 |
| Performance 測試 | 效能需求是否有對應驗證 |

#### 3.3 缺漏測試識別

將未被覆蓋的場景記錄為缺漏項目，每項包含：
- 來源（BDD Scenario 名稱或 SPEC 需求章節）
- 缺漏類型（單元/集成/API/E2E）
- 建議測試名稱（遵循 `MethodName_Scenario_ExpectedBehavior` 命名規範）
- 優先級（高/中/低）
- 理由說明

### Phase 4：產出風險報告並與使用者討論

#### 4.1 使用者確認問題撰寫規則

風險報告可以保留技術風險表與缺漏測試清單，但「需要使用者確認的問題」必須讓沒有接觸過專案的人也能判斷，且要優先描述實際功能、營運或資料面的影響。

每個待確認問題需包含：

1. **使用者或管理者會看到什麼差異**：用功能結果描述，不只寫 API、DTO、schema、測試名稱或技術名詞。
2. **若不處理會造成什麼後果**：例如功能無法使用、資料不會落地、管理者需要人工處理、正式資料可能被自動修改、後續 SPEC 會越界。
3. **建議做法**：用一到三個白話選項說明取捨，並標示 AI 建議的做法。
4. **需要使用者回答的句子**：問題本身應能用「接受 / 不接受 / 指定替代做法」回答。
5. **技術對照**：若需要保留技術細節，放在同一題的「對應文件 / 模組 / 測試」說明，不要把技術細節當成主要問題。

避免只問：

- 「是否接受新增 `SetupCheck.code`？」
- 「是否補 `SyncProductsToBackend_WithCategoryColumn_MapsCategoryToPayload`？」
- 「是否在 `Orders` append delivery 欄位？」

應改寫為：

- 「檢查失敗時，要不要提供更明確的錯誤代碼，讓部署者知道是哪張 Sheet 或哪個欄位錯？」
- 「商品分類欄位要不要真的接進現有商品同步流程？如果不接，分類只會存在 Google Sheets，Mini App 拿不到。」
- 「正式環境要不要禁止 setup validation 自動改 Sheet？如果不禁止，檢查流程可能直接變更正式欄位。」

若風險涉及敏感資料、安全、金流、正式資料 mutation、使用者可見流程、跨 SPEC 邊界或營運手冊，問題必須先用「實際會發生的功能情境」說明，再列技術名詞。

#### 4.2 風險報告格式

以下列格式呈現結果，**等待使用者確認後才進行 Phase 5**：

```markdown
## 📋 實作前風險與缺漏稽核報告

### 一、需求追溯摘要
- 涵蓋率：XX%（已追溯 / 總需求項目）
- 未追溯項目列表

### 二、技術風險（依嚴重度排序）

#### 🔴 高風險（必須在開發前解決）
| # | 風險描述 | 影響範圍 | 建議解決方案 |
|---|---------|---------|-------------|
| 1 | ...     | ...     | ...         |

#### 🟡 中風險（開發中需注意）
| # | 風險描述 | 影響範圍 | 建議解決方案 |
|---|---------|---------|-------------|
| 1 | ...     | ...     | ...         |

#### 🟢 低風險（可接受，已記錄）
| # | 風險描述 | 備註 |
|---|---------|------|
| 1 | ...     | ...  |

### 三、TDD 缺漏測試清單

#### 必補項目（高優先）
| # | 來源 | 缺漏類型 | 建議測試名稱 | 理由 |
|---|------|---------|-------------|------|
| 1 | ...  | ...     | ...         | ...  |

#### 建議補充（中優先）
| # | 來源 | 缺漏類型 | 建議測試名稱 | 理由 |
|---|------|---------|-------------|------|
| 1 | ...  | ...     | ...         | ...  |

### 四、建議與討論事項（白話功能影響確認）
1. [先描述實際功能、營運或資料面影響，再提出需要使用者決策的問題]
2. [可能影響架構的選擇，需說明使用者或管理者會看到的差異]
3. [需要釐清的需求模糊地帶，需提供建議做法與取捨]
```

### Phase 5：回寫缺漏到 TDD 文件

使用者確認報告後，將缺漏項目回寫到 TDD 文件：

#### 5.1 新增稽核補強章節

在 TDD 文件的對應測試層級中新增缺漏測試項目，格式與現有項目一致：

```markdown
### X.X [補強] 稽核補充測試 - [來源場景名稱]
**來源**: 實作前風險稽核 (YYYY-MM-DD)

- [ ] `MethodName_Scenario_ExpectedBehavior`
  - 測試 [描述]
  - 驗證 [斷言1]
  - 驗證 [斷言2]
```

#### 5.2 更新進度數字

將新增的測試計入 TDD 文件的進度統計：
- 更新「整體進度」的總測試數
- 更新對應層級的測試數
- 更新「分層進度追蹤」表格

#### 5.3 記錄稽核資訊

在 TDD 文件末尾新增稽核記錄：

```markdown
---

## 📝 稽核記錄

### YYYY-MM-DD 實作前風險與缺漏稽核
- 識別高風險：X 項
- 識別中風險：X 項
- 新增補強測試：X 項
- 稽核後總測試數：XX 項
```

## 禁止事項

- ❌ 未讀取所有必要文件就開始評估
- ❌ 只做表面檢查，未深入技術實現層面
- ❌ 發現問題卻不提出解決方案
- ❌ 未經使用者確認就直接修改 TDD 文件
- ❌ 重新生成整份 TDD 文件（應補齊而非重寫）
- ❌ 列出風險但不標示優先級
- ❌ 忽略 E2E 測試層的覆蓋檢查
