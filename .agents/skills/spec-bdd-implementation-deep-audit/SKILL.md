# SPEC/BDD/實作 深度稽核技能

此技能用於「TDD 開發完成後」的需求回歸檢查，目標是避免只看文件聲稱完成度，改為以**可追溯證據**確認真實完成狀態。

## 何時使用

- 使用者要求「原需求檢查」、「逐項比對規格與實作」
- TDD 文件已標示大量完成，但需要驗證真實性
- 需要把缺漏先回寫到 TDD 清單，再安排下一輪 Red-Green-Refactor

## 核心原則（務必遵守）

1. **深入檢查，不得抽樣**：SPEC 需求、BDD Scenario、TDD 測試項目都要逐項過表。
2. **證據導向**：每一個結論都必須附 `檔案路徑 + 行號`。
3. **名稱與行為雙重驗證**：不能只看測試名稱存在；要確認測試斷言真的覆蓋該需求。
4. **文件即現況**：TDD 中標記為 `[x]` 但無法追溯者，需改為待補並記錄原因。
5. **進度需重算**：依本次稽核後的實際狀態重新計算百分比，不沿用舊數字。

## 深度稽核流程

### Phase 1：需求面完整拆解（SPEC + BDD）

1. 逐段拆解 SPEC 功能需求、驗收標準、風險項目。
2. 逐一列出 BDD 全部 Scenario（含 Happy Path / Error / Edge / Alternative / Performance）。
3. 建立對照矩陣（需求/場景 → 實作檔案 → 測試檔案 → 狀態）。

### Phase 2：實作面逐項映射（程式 + 測試）

1. 在程式碼中找到每個需求對應實作（TS/Python/C# 等）。
2. 在測試中找到對應案例，確認：
   - 測試名稱是否對得上
   - 斷言是否驗證需求關鍵行為
3. 將每項標記為：
   - ✅ 已符合
   - ⚠️ 部分符合
   - ❌ 未符合/未實作

### Phase 3：TDD 真實性核對（重點）

1. 逐條檢查 TDD checklist（`- [x]/- [ ]`）。
2. 對每個 `[x]` 項目進行追溯：
   - 是否存在對應測試檔與測試案例
   - 是否有對應行為驗證
3. 無法追溯的 `[x]` 必須改為待補，並加上缺漏說明與建議測試名。

### Phase 4：缺漏回寫到 TDD

在 TDD 文件新增「稽核日期章節」，每個缺漏至少包含：

- 來源（SPEC 章節或 BDD Scenario 名稱）
- 現況證據（檔案路徑 + 行號）
- 建議新增測試名稱（可直接進 Red 階段）
- 優先級（高/中）

## 進度重算規範（強制）

### A. 整體進度百分比

以稽核後狀態計算：

- `total_items` = TDD checklist 總項數（`- [x]` + `- [ ]`）
- `verified_done_items` = `[x]` 且已通過追溯驗證的項數
- `pending_items` = `total_items - verified_done_items`
- `overall_percent` = `round(verified_done_items / total_items * 100, 1)`

### B. 分層進度百分比

對每個章節（Unit/Integration/E2E/Backend/補強）各自計算：

- `layer_percent` = `round(layer_verified_done / layer_total * 100, 1)`

### C. 文件同步位置

重算後需同步更新：

1. 「整體進度」區塊
2. 「分層進度追蹤」表格
3. 「當前 Sprint 狀態」
4. 「使用說明」中完成度敘述
5. 「最後更新」日期與狀態

## 產出格式（回覆使用者）

1. 一句話總結整體一致性評分（0-100）
2. 必補缺漏（高優先）
3. 建議補漏（中優先）
4. 已回寫到 TDD 的章節與重算後進度值

## 禁止事項

- ❌ 只做抽樣比對
- ❌ 沒有證據就判定「已完成」
- ❌ 保留無法追溯的 `[x]` 完成標記
- ❌ 沿用舊進度百分比而不重算
