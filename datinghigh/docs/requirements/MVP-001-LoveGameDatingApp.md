## 2026-11-06 配對架構與業務決策（優先於下列舊 MatchingSessions 規劃描述）

- 正式配對業務表為 **match_conditions、match_invitations、game_rounds、game_round_participants**；原規劃的 match_rounds 改名 game_rounds，match_active_round_claims 改為遊戲模組的 game_round_participants，保留 account_id UNIQUE 的全平台單場占用防護。
- user_profiles 持續作為玩家本人基本資訊、可分享欄位／化身與興趣生活資料的唯一來源；match_conditions 僅為合格玩家的受限配對搜尋投影，**不設 source_profile_revision 或跨表 revision 相等檢查**；只在配對必要資格／計分欄位有實質變更時，才在同一 D1 原子操作建立、更新或刪除。單純照片排序、名片分享設定、工作或自介等無關異動不更新投影，也不影響候選；原 user_profiles.revision 繼續用於 Profile 本身的 CAS。資料未完成時仍可保留 user_profiles，但不建立 match_conditions；gaming 由 game_round_participants 推導，不在條件表另存第二份遊戲狀態。
- 沒有「暫停被探索」功能／開關；現行 profileReady 完成且未在遊戲中、自動符合相容條件者即可出現在新候選搜尋。
- **已送出的有效 pending 邀請不因後續性向或偏好改動撤回、失效或重判**，仍可在 72 小時內按原邀請成立時雙向相容的效力接受；新搜尋及新發邀請使用更新後的條件。接受舊邀請仍須驗有效登入、active 帳號、成年、有效化身、尚未進入其他遊戲、期限及永久 pair 排除。真正基本資格失效才可用 eligibility_changed，不可用於單純改性向。
- 候選先從 match_conditions 篩 ready、雙向性向，NOT EXISTS 查 declined／ended／遊戲占用，pending 必須區分 incoming 可接受與 outgoing 等候。對全部合格候選先計分排序再分頁，清單只回ID、分數及狀態；畫面再按需取得安全人物卡（預取少量），避免一次取得全部對象資訊。

## 需求概述

將交友配對軟體與戀愛養成遊戲深度結合，讓認識初期藉由線上虛擬人物與故事情境展開互動，透過選項建議化解剛認識時的尷尬，並隨著雙方好感度數據提升，分階段解鎖線上趣味小遊戲以及推薦線下實體合作通路活動（如實境解謎、手作工作坊等），最後若任一方感到不適亦可隨時平順結束互動。

### 重要注意事項與設計參考

概念已產出於：`datinghigh/prototypes/prototype.v2`，遊戲設計風格必須與 prototype 相同。

- 延續視覺小說／`ADV` 的人物立繪、場景背景、氣泡對話框、粉玫瑰與深紫色調、半透明面板及劇情逐句推進形式。
- 正式產品使用 `React Native + Expo`，主要支援 `iOS`／`Android`，並支援 Web；原型的 `Next.js` 實作作為畫面與互動參考。
- 原型目前為固定對象「夏樹」與結構化模擬資料，沒有真實雙人連線、外部 AI 或金流串接。正式配對與雙方同意須由兩名使用者各自操作，不能以原型的自動回覆代替驗收。
- 原型 `app/content.ts` 的線上／線下門檻為 40／75，且只有單一好感度；正式規則以本文件的雙方個人好感度、親密度及 10／25／50／60／85 門檻為準。
- 「親密度」為原「總體好感度」的新名稱，等於雙方個人好感度的平均；不新增獨立分數或修改平均計算。對外仍只顯示親密度區間／等級，個人分數僅本人可見。

## 主要需求

### 核心功能（六大核心需求規劃解決方案）

1. **虛擬人物形象建立**
   - 化身有兩條可選路徑：**免費內建插畫角色（男性風格 8 款、女性風格 8 款，共 16 款）**可直接選用；**AI 客製化生成**屬未來付費功能，本 MVP 以鎖頭標示，點擊即可使用，不真的收費。
   - 客製化形象模組：使用個人資料中已上傳的多張本人照片，根據照片與 AI 內建指示，同一輪最多依序完成 **4 張**，每次只產生1張，成功可提前採用插畫風但盡量保留本人五官與相似度的人物結果，讓本人選擇最滿意的 **1 張**作未來遊戲使用的化身；可用 Gemini 真實 API 驗證。
   - 個人真人照獨立於 AI 生成流程維護，每人至多 5 張；上傳單張原始檔上限 8 MiB，經可供後續功能重用的共用方法壓縮至**每張不超過 200 KB**後保存。上傳前提醒：「請提供自己最滿意的個人照，未來同意的情況下提供對方交換名片時查閱」；該照片也作為未來經雙方同意才公開的名片內容，不因生成後而預設清除。
   - 化身暱稱與個性設定：提供個性小標籤（如「溫暖貓派」、「週末戶外探險家」），增加角色辨識度與趣味。
   - 個資隱私防護：初期不直接暴露真實照片與敏感聯絡資訊；僅限該輪雙方同意交換名片後，可在受授權查閱介面讀取對方目前保存的本人真人照（200 KB 壓縮版本），不使用公用照片 URL。

2. **深入交友欄位與擇偶偏好設定**
   - 深度興趣標籤庫：涵蓋文創生活、戶外運動、美食探索、影劇動漫、心理測驗等維度。
   - 生活型態與價值觀：休閒習慣、作息偏好、期待互動頻率等結構化欄位，並提供**工作／職業**欄位，作為本人資料及同意後名片的內容。
   - 配對條件偏好：設定期待的年齡區間、地理區域以及共同興趣加權。

3. **智能條件配對與互動發起**
   - 契合度演算法：依據雙方填寫之興趣標籤、生活型態與擇偶條件，計算契合度指數。
   - 配對確認開啟遊戲：雙方確認契合意向後，立即建立專屬情境聊天室，展開雙人戀愛養成互動流程。

4. **戀愛養成沉浸式劇情破冰與對話框系統**
   - 專屬虛擬人物對話框：採用戀愛養成 ADV 遊戲風格之精緻人物立繪站位與氣泡對話框，營造強烈代入感。
   - 初始劇情故事情境：系統依據雙方共同興趣，給予客製化的開場場景（如「文青咖啡館偶遇」、「雨天書店避雨」等）。
   - 破冰選項建議：提供 3 組不同性格面向的初始回應建議按鈕，點擊即可傳送生動台詞，徹底化解開場尷尬。
   - 此MVP需依據上述欄位設計10種不同劇情，劇情公式採用：
     1. 時間：`{形容詞}{時間}`，例如：月黑風高的晚上、天氣悶熱的下午...
     2. 空間：`{地點}`，例如：在咖啡廳、在圖書館...
     3. 事件：發生了什麼事情

5. **好感度數據提升與雙階段互動解鎖**
   - 好感度數值即時追蹤：
     1. 分為個人好感度與親密度，親密度是雙方個人好感度的平均，只有個人好感度會被異動(包含系統的算分)，個人本身也可以隨時自由調整個人好感度分數。
     2. 親密度由系統以雙方個人好感度的平均計算，用於各階段門檻判定；雙方畫面僅顯示親密度區間／等級，不顯示精確平均分數或可還原精確平均分數的進度。個人好感度只呈現給自己。區間與等級的對應方式於後續規格定義。
     3. 依雙方回應積極度、共同選擇默契度即時累計個人好感度點數，以進度條與等級動態呈現。
     4. 於遊戲中各階段皆提供直接的個人好感度問卷回饋，作為其中一項指標加分或減分，針對想得知對方對於回饋的內容，提供付費解鎖功能(本MVP只以鎖頭標記，點擊後取得即可)。
   - 線上階段解鎖（門檻一）：低門檻（親密度 10 至未滿 60），且隨好感度會出現不同難度/曖昧程度的遊戲，填補實體約會階段前的互動，並確認可進到下階段
     1. 此MVP設計2種曖昧互動小遊戲(例如：雙人默契二選一小遊戲)，隨門檻一的好感度不同觸發。
     2. 此MVP設計3種線上協力解謎與趣味支線劇情任務(例如：心理測驗、情境模擬、算命...等等)，隨門檻一的好感度不同觸發。
     3. 親密度達到 25 分時顯示「交換名片」功能，可由一方發起，雙方同意後才揭露彼此在配對前開始填寫、並可持續更新的**目前個人資料（含工作／職業與上傳的真人照片壓縮版本）**；不另要求填寫名片或建立快照。邀請可以重送，拒絕不影響任一方個人好感度或親密度。25 分只判斷入口是否顯示，不另加掉分取消邀請或重新鎖定已交換資料的規則；交換仍受雙方同意及該輪有效性約束，終止後不得再讀取新更新的資料。
     4. 親密度達到50分時，提供[約會]功能，可以提前觸發門檻二的線下活動建議，如果雙方成功同意約會，直接將雙方個人好感度各設為65分（包含原本高於65分的情況），再重新計算親密度。
   - 實體約會階段解鎖（門檻二）：高門檻（親密度 60 至未滿 85），好感度要高到一個程度
     1. 此MVP設計5種真實的線下活動建議，在劇情發展中自然推薦線下實體互動活動（如實境解謎、手作工作坊、文創展覽、公益參與），於門檻二親密度到達時推薦雙方。
     2. 門檻二階段定期以好感度問卷回饋，主要作為線下雙方好感度確認的方式，進行加分或減分。
     3. 雙方成功同意約會，直接將雙方個人好感度各設為65分（包含原本高於65分的情況）；如果被任一方拒絕，雙方個人好感度各設為50分；兩種結果皆重新計算親密度。
   - 告白功能(門檻三)：親密度85分以上開放，用一封情書的形式由其中一方填寫，進行心動告白。

6. **平順退出與邊界保護機制**
   - 好感度過低主動偵測：互動冷卻或好感度低於安全門檻時，主動給予平順結束機制。
   - 語境識別結束防護：系統自動識別「不想繼續」、「掰掰」、「先到這邊」等明確結束語境。
   - 隨時一鍵安全退出：任何一方點擊「結束本輪互動」，即刻平順終止該輪對話與遊戲，停止後續訊息，保障使用者人際安全。

## 架構選擇

來源架構為 `React Native + Expo` 前端、`.NET` 後端、SQLite 資料庫、Cloudflare R2 Object 檔案庫與全 Cloudflare 部署。依 D-003，正式資料庫調整為 D1；SQLite 的本地使用需求保留。

| 項目 | 規劃方向 | 實作邊界 |
|------|----------|----------|
| 前端 | `React Native + Expo`，支援 `iOS`／`Android`／Web | 延續 `prototype.v2` 視覺與劇情操作；Web 部署及行動版建置方式於基礎 SPEC 定義 |
| 後端 | `.NET`，部署 Cloudflare Containers | 保留 `.NET` 業務邏輯；Worker 負責必要的容器入口與雲端資源連接 |
| 正式資料庫 | Cloudflare D1（SQLite 語意） | 透過雲端資料存取介面使用 D1，不以容器內磁碟的 `.db` 檔作正式持久化來源 |
| 本地資料庫 | SQLite／D1 本地環境 | 可測試、查詢、修改本地資料；涉及 D1 的整合以 D1 本地環境驗證，不假設原生 SQLite 的所有功能皆與 D1 相同 |
| 檔案庫 | Cloudflare R2 Object Storage | 保存照片與生成化身等檔案；原始照片與公開化身的讀取權限分開設計 |
| 雲端部署 | 全部自有服務部署於 Cloudflare | AI 推論的供應商、模型及資料傳送方式於化身 SPEC 選定；本階段未承諾特定模型能力 |

### 設計需求

1. 本地也要能有 localdb 可以測試、查看修改資料。
2. 本地與正式資料分開；提供可重現的資料結構建立、初始資料與本地查改操作方式，具體命令與工具於基礎 SPEC 設計。
3. 2026-10-24 已確認目前 Windows 開發環境有 SQLite CLI `3.44.3`、Python SQLite `3.50.4`、`.NET SDK 9.0.200` 與 `10.0.204`；已完成臨時本地資料庫的寫入及重新開啟讀取。這項結果僅代表本地 SQLite 可用，尚未建立本專案的 `.NET` 資料存取、D1 或部署設定。

### 017：以 Access Token／Refresh Token 延續並撤銷登入

**驗收標準**：

- `AC-017-01`：帳密與 Google 登入均核發平台 Access Token／Refresh Token；兩者分工及期限明確，Google ID／Access Token 不作平台 API 憑證。
- `AC-017-02`：Refresh Token 輪替具有原子性與重放偵測；依D-020，已消耗 token 於消耗後 30 秒內視為回應遺失重試（不撤銷），超過寬限重放才撤銷整個登入；過期、撤銷、重用及錯誤類型的 token 依規則拒絕。
- `AC-017-03`：Web 與行動版各有適當的安全儲存／傳輸、到期恢復及網路結果不明處理；同Account僅最新成功登入有效，舊裝置不可refresh復活。依D-021，Web 不限分頁數，舊分頁以回應標頭 session 比對與 401 `SESSION_REVOKED` 重驗並清除私人畫面，已知「同瀏覽器另一分頁以不同帳號登入」的短暫風險已記錄；同一端的多請求合併一次refresh，不無限refresh或盲目重送已可能執行的動作。
- `AC-017-04`：登出、修改密碼、帳號復原及安全憑證變更撤銷其對應登入狀態；即使 Access Token 尚未到期，也不能繞過已撤銷狀態繼續存取。

### 020：雙方同意後交換名片

**身為** 互動中的使用者，**我想要** 在親密度達標時邀請對方交換名片，**以便** 在雙方同意後了解彼此從配對前開始填寫、之後可持續更新的目前個人資料及真人照片。

**驗收標準**：

- `AC-020-01`：以內部親密度判定入口，達到 25 分顯示「交換名片」，未滿 25 分不顯示；不因新增門檻回傳精確親密度或對方個人分數。
- `AC-020-02`：名片內容引用使用者在配對前開始建立、後續可編修的**同一份目前個人資料**（含工作／職業與本人真人照的壓縮版本），不另建立／填寫名片或保存配對時快照；具體欄位對應由 `SPEC-001-AvatarAndPreferences` 定義，認證帳號 DTO 與憑證不作名片資料來源。
- `AC-020-03`：該輪任一參與者可發起，雙方同意後才可互看名片；待回覆或拒絕時不得取得尚未同意揭露的資料，該輪以外的使用者不得讀取或回覆。
- `AC-020-04`：任一方拒絕交換名片，不改變任一方個人好感度或親密度；不沿用約會拒絕時各設為 50 的規則。
- `AC-020-05`：邀請可以重送，重送不改變分數，也不能代替對方同意。25 分只控制功能入口顯示，不另加因掉分而取消待回覆邀請或重新鎖定已交換資料的規則。
- `AC-020-06`：該輪互動終止後，待處理邀請不得繼續完成交換或揭露新資料；雙方同意及揭露狀態限該輪使用，不使其他配對自動取得名片權限。
- `AC-020-07`：交換同意後每次依現有有效授權讀取**即時的本人資料與現有照片**，資料更新／照片替換／刪除要反映，不使用配對當下或交換當下的資料快照；未獲同意或已終止的互動不得據此取得新更新的資料。

## 畫面操作流程

### 1. 化身與偏好設定

```text
開啟 iOS／Android／Web 應用
  ↓
以 Email 註冊並完成收件碼，或以 Google 登入（Email 未註冊時直接建帳，不需收件碼）
  ↓
同一 Email 全域檢查，已註冊／第三方同地址不可再建帳
  ↓
取得平台 Access／Refresh Token（到期依規則刷新，登出撤銷）
  ↓
個人資料：上傳／替換／刪除最多5張真人照（提醒用途 → 共用壓縮至 ≤200 KB → 私人保存）
  ↓
選擇遊戲化身：
  ├─ 免費：男性風格8款／女性風格8款內建3:4半身立繪中選1款
  └─ AI：點鎖頭進入 → 顯示第三方送照提醒 → 按「開始產生第1張」 → 每次真產出1張（最多4張）→ 可採用或再產下一張／回選先前候選 → 「採用這張」二次確認未來重生費用（MVP現階段免費） → 正式保存1張
  ↓
填寫暱稱、個性、自介、工作／職業、興趣、生活型態、價值觀、年齡／地區偏好與興趣加權
  ↓
進入配對流程（初期只有遊戲化身；雙方同意名片交換後才查閱目前真人照與工作資料）
```

### 2. 配對、劇情與好感度

```text
依條件計算契合度 → 查看候選對象 → 各自確認意向
  ├─ 尚未雙方確認 → 保持待確認
  └─ 雙方確認 → 建立專屬情境聊天室
                    ↓
             從 10 種劇情依共同興趣選擇開場
                    ↓
             人物立繪與對話框 → 3 組破冰回應 → 雙向對話
                    ↓
             回應／默契事件或問卷調整個人分數
             （本人也可隨時自由調整自己的分數）
                    ↓
             系統重算平均 → 顯示親密度區間／等級 → 判斷內容門檻
                    ↓
             各階段問卷 → 自己填寫 → 鎖頭點擊取得對方回饋內容
```

### 3. 線上遊戲、交換名片、線下約會與告白

```text
依內部親密度判定目前可用功能
  ├─ 10 至未滿 60 → 依好感度開啟 2 種小遊戲與 3 種任務
  │                   ↓
  │                 選擇可用內容 → 雙方參與 → 完成互動與結果回饋
  ├─ 達到 25 → 顯示「交換名片」→ 任一方發起邀請
  │                              ├─ 雙方同意 → 授權互看目前個人資料、工作／職業與真人照的壓縮保存版本
  │                              ├─ 待回覆 → 尚不揭露，可重送邀請
  │                              └─ 拒絕 → 不改分數，可重送邀請
  ├─ 達到 50 → 可提前使用「約會」並查看線下活動建議
  ├─ 60 至未滿 85 → 劇情推薦 5 種真實線下活動 → 定期問卷
  └─ 達到 85 → 填寫情書 → 向對方告白

約會邀請 → 對方回覆
  ├─ 雙方同意 → 個人分數各設為 65 → 重算平均
  └─ 任一方拒絕 → 個人分數各設為 50 → 重算平均
```

交換名片的 25 分只控制入口顯示，不另設掉分取消邀請或重新鎖定規則；仍須雙方同意且該輪互動未終止，不能用重送繞過同意。名片讀取沿用配對前開始建立、之後可持續更新的目前個人資料；其中包含工作／職業與**本人真人照的 200 KB 壓縮版本**，但僅在有效雙方同意後才開放受控查閱。登入 Email、精確生日、原始未壓縮照片、私人分數與登入憑證依然禁止揭露。

### 4. 隨時退出

```text
該輪互動的任一階段
  ├─ 冷卻／低好感 → 主動提示平順結束
  ├─ 明確結束語境 → 啟動結束防護
  └─ 任一方點擊「結束本輪互動」 → 即刻結束該輪
                                          ↓
                              停止後續訊息及名片交換／遊戲／約會／告白推進
                                          ↓
                                     顯示結束狀態
```

## 主要需求

### 核心功能（六大核心需求規劃解決方案）

1. **虛擬人物形象建立**
   - 化身有兩條可選路徑：**免費內建插畫角色（男性風格 8 款、女性風格 8 款，共 16 款）**可直接選用；**AI 客製化生成**屬未來付費功能，本 MVP 以鎖頭標示，點擊即可使用，不真的收費。
   - 客製化形象模組：使用個人資料中已上傳的多張本人照片，根據照片與 AI 內建指示，同一輪最多依序完成 **4 張**，每次只產生1張，成功可提前採用插畫風但盡量保留本人五官與相似度的人物結果，讓本人選擇最滿意的 **1 張**作未來遊戲使用的化身；可用 Gemini 真實 API 驗證。
   - 個人真人照獨立於 AI 生成流程維護，每人至多 5 張；上傳單張原始檔上限 8 MiB，經可供後續功能重用的共用方法壓縮至**每張不超過 200 KB**後保存。上傳前提醒：「請提供自己最滿意的個人照，未來同意的情況下提供對方交換名片時查閱」；該照片也作為未來經雙方同意才公開的名片內容，不因生成後而預設清除。
   - 化身暱稱與個性設定：提供個性小標籤（如「溫暖貓派」、「週末戶外探險家」），增加角色辨識度與趣味。
   - 個資隱私防護：初期不直接暴露真實照片與敏感聯絡資訊；僅限該輪雙方同意交換名片後，可在受授權查閱介面讀取對方目前保存的本人真人照（200 KB 壓縮版本），不使用公用照片 URL。

2. **深入交友欄位與擇偶偏好設定**
   - 深度興趣標籤庫：涵蓋文創生活、戶外運動、美食探索、影劇動漫、心理測驗等維度。
   - 生活型態與價值觀：休閒習慣、作息偏好、期待互動頻率等結構化欄位，並提供**工作／職業**欄位，作為本人資料及同意後名片的內容。
   - 配對條件偏好：設定期待的年齡區間、地理區域以及共同興趣加權。

3. **智能條件配對與互動發起**
   - 契合度演算法：依據雙方填寫之興趣標籤、生活型態與擇偶條件，計算契合度指數。
   - 配對確認開啟遊戲：雙方確認契合意向後，立即建立專屬情境聊天室，展開雙人戀愛養成互動流程。

4. **戀愛養成沉浸式劇情破冰與對話框系統**
   - 專屬虛擬人物對話框：採用戀愛養成 ADV 遊戲風格之精緻人物立繪站位與氣泡對話框，營造強烈代入感。
   - 初始劇情故事情境：系統依據雙方共同興趣，給予客製化的開場場景（如「文青咖啡館偶遇」、「雨天書店避雨」等）。
   - 破冰選項建議：提供 3 組不同性格面向的初始回應建議按鈕，點擊即可傳送生動台詞，徹底化解開場尷尬。
   - 此MVP需依據上述欄位設計10種不同劇情，劇情公式採用：
     1. 時間：`{形容詞}{時間}`，例如：月黑風高的晚上、天氣悶熱的下午...
     2. 空間：`{地點}`，例如：在咖啡廳、在圖書館...
     3. 事件：發生了什麼事情

5. **好感度數據提升與雙階段互動解鎖**
   - 好感度數值即時追蹤：
     1. 分為個人好感度與親密度，親密度是雙方個人好感度的平均，只有個人好感度會被異動(包含系統的算分)，個人本身也可以隨時自由調整個人好感度分數。
     2. 親密度由系統以雙方個人好感度的平均計算，用於各階段門檻判定；雙方畫面僅顯示親密度區間／等級，不顯示精確平均分數或可還原精確平均分數的進度。個人好感度只呈現給自己。區間與等級的對應方式於後續規格定義。
     3. 依雙方回應積極度、共同選擇默契度即時累計個人好感度點數，以進度條與等級動態呈現。
     4. 於遊戲中各階段皆提供直接的個人好感度問卷回饋，作為其中一項指標加分或減分，針對想得知對方對於回饋的內容，提供付費解鎖功能(本MVP只以鎖頭標記，點擊後取得即可)。
   - 線上階段解鎖（門檻一）：低門檻（親密度 10 至未滿 60），且隨好感度會出現不同難度/曖昧程度的遊戲，填補實體約會階段前的互動，並確認可進到下階段
     1. 此MVP設計2種曖昧互動小遊戲(例如：雙人默契二選一小遊戲)，隨門檻一的好感度不同觸發。
     2. 此MVP設計3種線上協力解謎與趣味支線劇情任務(例如：心理測驗、情境模擬、算命...等等)，隨門檻一的好感度不同觸發。
     3. 親密度達到 25 分時顯示「交換名片」功能，可由一方發起，雙方同意後才揭露彼此在配對前開始填寫、並可持續更新的**目前個人資料（含工作／職業與上傳的真人照片壓縮版本）**；不另要求填寫名片或建立快照。邀請可以重送，拒絕不影響任一方個人好感度或親密度。25 分只判斷入口是否顯示，不另加掉分取消邀請或重新鎖定已交換資料的規則；交換仍受雙方同意及該輪有效性約束，終止後不得再讀取新更新的資料。
     4. 親密度達到50分時，提供[約會]功能，可以提前觸發門檻二的線下活動建議，如果雙方成功同意約會，直接將雙方個人好感度各設為65分（包含原本高於65分的情況），再重新計算親密度。
   - 實體約會階段解鎖（門檻二）：高門檻（親密度 60 至未滿 85），好感度要高到一個程度
     1. 此MVP設計5種真實的線下活動建議，在劇情發展中自然推薦線下實體互動活動（如實境解謎、手作工作坊、文創展覽、公益參與），於門檻二親密度到達時推薦雙方。
     2. 門檻二階段定期以好感度問卷回饋，主要作為線下雙方好感度確認的方式，進行加分或減分。
     3. 雙方成功同意約會，直接將雙方個人好感度各設為65分（包含原本高於65分的情況）；如果被任一方拒絕，雙方個人好感度各設為50分；兩種結果皆重新計算親密度。
   - 告白功能(門檻三)：親密度85分以上開放，用一封情書的形式由其中一方填寫，進行心動告白。

6. **平順退出與邊界保護機制**
   - 好感度過低主動偵測：互動冷卻或好感度低於安全門檻時，主動給予平順結束機制。
   - 語境識別結束防護：系統自動識別「不想繼續」、「掰掰」、「先到這邊」等明確結束語境。
   - 隨時一鍵安全退出：任何一方點擊「結束本輪互動」，即刻平順終止該輪對話與遊戲，停止後續訊息，保障使用者人際安全。

## 架構選擇

來源架構為 `React Native + Expo` 前端、`.NET` 後端、SQLite 資料庫、Cloudflare R2 Object 檔案庫與全 Cloudflare 部署。依 D-003，正式資料庫調整為 D1；SQLite 的本地使用需求保留。

| 項目 | 規劃方向 | 實作邊界 |
|------|----------|----------|
| 前端 | `React Native + Expo`，支援 `iOS`／`Android`／Web | 延續 `prototype.v2` 視覺與劇情操作；Web 部署及行動版建置方式於基礎 SPEC 定義 |
| 後端 | `.NET`，部署 Cloudflare Containers | 保留 `.NET` 業務邏輯；Worker 負責必要的容器入口與雲端資源連接 |
| 正式資料庫 | Cloudflare D1（SQLite 語意） | 透過雲端資料存取介面使用 D1，不以容器內磁碟的 `.db` 檔作正式持久化來源 |
| 本地資料庫 | SQLite／D1 本地環境 | 可測試、查詢、修改本地資料；涉及 D1 的整合以 D1 本地環境驗證，不假設原生 SQLite 的所有功能皆與 D1 相同 |
| 檔案庫 | Cloudflare R2 Object Storage | 保存照片與生成化身等檔案；原始照片與公開化身的讀取權限分開設計 |
| 雲端部署 | 全部自有服務部署於 Cloudflare | AI 推論的供應商、模型及資料傳送方式於化身 SPEC 選定；本階段未承諾特定模型能力 |

### 設計需求

1. 本地也要能有 localdb 可以測試、查看修改資料。
2. 本地與正式資料分開；提供可重現的資料結構建立、初始資料與本地查改操作方式，具體命令與工具於基礎 SPEC 設計。
3. 2026-10-24 已確認目前 Windows 開發環境有 SQLite CLI `3.44.3`、Python SQLite `3.50.4`、`.NET SDK 9.0.200` 與 `10.0.204`；已完成臨時本地資料庫的寫入及重新開啟讀取。這項結果僅代表本地 SQLite 可用，尚未建立本專案的 `.NET` 資料存取、D1 或部署設定。

### 001：建立專屬虛擬人物

**身為** 使用者，**我想要** 免費選用內建插畫人物，或將個人資料中上傳的多張照片交由 AI 依序逐張產生最多四款可選化身，並設定暱稱與個性，**以便** 在不公開真人照片的初期先用喜歡的角色開始認識對方。

**驗收標準**：

- `AC-001-01`：支援多張照片輸入，依照片與 AI 內建指示生成專屬虛擬人物，風格與 `prototype.v2` 一致；**免費與 AI 人物統一直式 3:4、半身至腰部立繪，五官清晰、背景簡潔，避免拉伸或裁斷臉部**。
- `AC-001-02`：可以設定化身暱稱與個性小標籤，並於互動畫面使用該化身資料。
- `AC-001-03`：免付費內建男性風格 8 款、女性風格 8 款共 16 款插畫人物供直接選擇，不必使用 AI；角色分組不限制使用者選擇。
- `AC-001-04`：AI 化身為未來付費功能，**本 MVP 仍可免費使用且不扣款**；產圖頁固定顯示第三方 Gemini 送照提醒。本人點「開始產生第1張」後，每個請求只確實產生1張，依序可選「採用這張」或「產生下一張」，最多累積4張成功候選；之前未採用的圖片仍可回頭比較及選擇。按「採用這張」先出現二次確認：「採用後本輪結束；未來正式付費上線後重新產生會依當時方案收費（目前免費）」；確認後只永久保存1張、清理其餘候選，取消則保留本輪不收費。每次逾時／失敗不能算成功或產生假圖，不覆寫既有化身；同輪與同帳號並發／重送不得超出4張或重複計費。
- `AC-001-05`：真人照片是持續可維護的個人資料，上傳時顯示「請提供自己最滿意的個人照，未來同意的情況下提供對方交換名片時查閱」；每人最多 5 張、單張上傳上限 8 MiB，所有保存照片先使用可重用的共用圖片壓縮能力壓至 **≤200 KB**，AI 生成沿用已保存照片，不要求每次重新上傳。
- `AC-001-06`：AI 生成要與原型插畫風格一致，並盡量保留來源真人照片五官與相似度，不得因刻意過度變形而失真；可在本地／受控測試環境以 Gemini 真實服務驗證，金鑰不得暴露給 client 或寫入程式庫。

- `AC-012-01`：互動冷卻或好感度低於安全門檻時主動提供平順結束機制。
- `AC-012-02`：可自動識別「不想繼續」、「掰掰」、「先到這邊」等明確結束語境並啟動結束防護。
- `AC-012-03`：任一方可在該輪互動的任何階段使用「結束本輪互動」，即刻終止該輪對話與遊戲。
- `AC-012-04`：結束後停止該輪後續訊息；未完成的名片交換、小遊戲、問卷、約會與告白操作亦不得繼續推進該輪，待處理名片交換不得再完成或揭露新資料。

### 013：在行動裝置與 Web 使用相同遊戲體驗

**身為** 使用者，**我想要** 在 `iOS`／`Android` 與 Web 完成主要流程，**以便** 使用適合自己的裝置參與互動。

**驗收標準**：

- `AC-013-01`：前端採 `React Native + Expo`，主要流程可在 `iOS`／`Android` 與 Web 操作。
- `AC-013-02`：跨平台維持 `prototype.v2` 的遊戲設計風格，並使用相同的配對、分數、門檻與退出規則。

### 014：在本地測試並查改資料

**身為** 開發者，**我想要** 在自己的電腦使用本地資料庫測試、查看與修改資料，**以便** 開發及排查互動流程問題。

**驗收標準**：

- `AC-014-01`：可建立與運行本專案的本地 SQLite／D1 資料環境，查詢及修改測試資料。
- `AC-014-02`：提供本地資料建立與查改操作方式；重啟後仍可讀取已保存資料，本地查改不影響正式資料。

### 015：依指定技術架構保存及部署服務

**身為** 維護者，**我想要** 以 `.NET`、D1 與 R2 在 Cloudflare 部署服務，**以便** 依已確認架構運行正式產品並保存資料。

**驗收標準**：

- `AC-015-01`：`.NET` 後端部署於 Cloudflare Containers，使用必要的 Worker 連接與部署設定。
- `AC-015-02`：正式資料存於 D1，照片與化身檔案存於 R2，不依賴容器暫存磁碟保存正式資料。

### 016：使用 Google 登入並明確連結帳號

**身為** 使用者，**我想要** 在行動與 Web 使用 Google 登入，並能在本人授權後連結既有帳號，**以便** 使用方便的登入方式存取同一份平台資料。

**驗收標準**：

- `AC-016-01`：`iOS`／`Android`／Web 支援真實 Google OAuth／OIDC 登入；成功後使用平台自己的帳號與權杖存取資料。
- `AC-016-02`：後端驗證 Google credential 的簽章、來源、對象與期限；SDK 取消／過時結果由 App 管理，偽造／過期／錯 app 的證明不核發平台權杖，Web 保留 CSRF 防護。依 D-013 不建第三方登入挑戰表、不要求每份有效 Google ID Token 僅能交換一次；連結仍由後端驗提交當下本人授權。
- `AC-016-03`：同一 Google 固定使用者識別在不同裝置先後登入對應同一平台帳號；依D-017新登入成功使舊登入失效，不允許同時有效。依D-023，Google 首次登入且 Email 未註冊時直接建立帳號與登入（不需收件碼），但 Email 僅在網域為 gmail.com 或 hd claim 與 Email 網域相符時可信，否則拒絕；Email 已註冊時回衝突，不以相同 Email 自動合併。既有帳號連結需本人明確授權（依D-025：已登入且 Google 驗證的 Email 等於本人 Email，不需密碼、不踢登出）；不將 Google 姓名／真實頭像公開為遊戲化身。
- `AC-016-04`：Google 連結／解除與登入方式管理包含在 `SPEC-001-PlatformFoundation`，不得因解除而失去最後的登入方式；依D-025，連結不需 currentPassword、不使既有登入失效，解除需 currentPassword 並使既有登入狀態失效。

### 017：以 Access Token／Refresh Token 延續並撤銷登入

**身為** 已登入的使用者，**我想要** 透過 Access Token 存取功能，並在短效權杖到期時使用 Refresh Token 延續登入，**以便** 兼顧操作連續性與登入安全。

**驗收標準**：

- `AC-017-01`：帳密與 Google 登入均核發平台 Access Token／Refresh Token；兩者分工及期限明確，Google ID／Access Token 不作平台 API 憑證。
- `AC-017-02`：Refresh Token 輪替具有原子性與重放偵測；依D-020，已消耗 token 於消耗後 30 秒內視為回應遺失重試（不撤銷），超過寬限重放才撤銷整個登入；過期、撤銷、重用及錯誤類型的 token 依規則拒絕。
- `AC-017-03`：Web 與行動版各有適當的安全儲存／傳輸、到期恢復及網路結果不明處理；同Account僅最新成功登入有效，舊裝置不可refresh復活。依D-021，Web 不限分頁數，舊分頁以回應標頭 session 比對與 401 `SESSION_REVOKED` 重驗並清除私人畫面，已知「同瀏覽器另一分頁以不同帳號登入」的短暫風險已記錄；同一端的多請求合併一次refresh，不無限refresh或盲目重送已可能執行的動作。
- `AC-017-04`：登出、修改密碼、帳號復原及安全憑證變更撤銷其對應登入狀態；即使 Access Token 尚未到期，也不能繞過已撤銷狀態繼續存取。

### 018：Email 註冊、認證碼與重複檢查

**身為** 使用者，**我想要** 以 Email 註冊並輸入認證碼證明收件權，**以便** 安全建立可登入的唯一帳號。

**驗收標準**：

- `AC-018-01`：登入帳號使用 Email，註冊具備請求認證碼、輸入確認與重寄流程；未確認前不得取得可使用的帳號／平台登入權杖。
- `AC-018-02`：本機啟動時認證碼以後端 log 呈現；所有 server 環境實際寄到 Email，不可以 log／假寄送代替。依D-026，寄送失敗時註冊與重寄回明確失敗（503），不提供投遞狀態機。
- `AC-018-03`：Email 已註冊、由第三方帳號使用或跨方式並行註冊時不可重複；Google 與 Email 註冊共用同一 Email 唯一規則（Google 首次登入遇已註冊 Email 回衝突），不自動合併他人帳號。
- `AC-018-04`：認證碼有到期、重寄冷卻、錯誤上限、用途綁定及單次使用規則；錯誤／過期／重用不得完成註冊，細部數值在 SPEC 固定。

### 019：忘記密碼與 Email 重設

**身為** 忘記密碼的使用者，**我想要** 透過註冊 Email 收取認證碼並設定新密碼，**以便** 恢復帳號使用。

**驗收標準**：

- `AC-019-01`：提供忘記密碼入口、Email 寄碼、驗碼／重寄、輸入新密碼與成功後重新登入的完整流程；本機／server 寄送方式同 `AC-018-02`。
- `AC-019-02`：錯誤、過期、重複使用、用途不符或不存在帳號的挑戰不能修改密碼；未知Email使用相同通用訊息，不直接明示註冊狀態。依D-018不加人為固定等待，接受回應時間差的剩餘風險，不承諾完全防止推測地址是否存在。
- `AC-019-03`：成功重設後新密碼可登入，舊密碼與所有舊 Access／Refresh 登入狀態失效；Google 綁定保留，僅第三方登入帳號也可經有效 Email 碼設定本地密碼。

### 020：雙方同意後交換名片

**身為** 互動中的使用者，**我想要** 在親密度達標時邀請對方交換名片，**以便** 在雙方同意後了解彼此從配對前開始填寫、之後可持續更新的目前個人資料及真人照片。

**驗收標準**：

- `AC-020-01`：以內部親密度判定入口，達到 25 分顯示「交換名片」，未滿 25 分不顯示；不因新增門檻回傳精確親密度或對方個人分數。
- `AC-020-02`：名片內容引用使用者在配對前開始建立、後續可編修的**同一份目前個人資料**（含工作／職業與本人真人照的壓縮版本），不另建立／填寫名片或保存配對時快照；具體欄位對應由 `SPEC-001-AvatarAndPreferences` 定義，認證帳號 DTO 與憑證不作名片資料來源。
- `AC-020-03`：該輪任一參與者可發起，雙方同意後才可互看名片；待回覆或拒絕時不得取得尚未同意揭露的資料，該輪以外的使用者不得讀取或回覆。
- `AC-020-04`：任一方拒絕交換名片，不改變任一方個人好感度或親密度；不沿用約會拒絕時各設為 50 的規則。
- `AC-020-05`：邀請可以重送，重送不改變分數，也不能代替對方同意。25 分只控制功能入口顯示，不另加因掉分而取消待回覆邀請或重新鎖定已交換資料的規則。
- `AC-020-06`：該輪互動終止後，待處理邀請不得繼續完成交換或揭露新資料；雙方同意及揭露狀態限該輪使用，不使其他配對自動取得名片權限。
- `AC-020-07`：交換同意後每次依現有有效授權讀取**即時的本人資料與現有照片**，資料更新／照片替換／刪除要反映，不使用配對當下或交換當下的資料快照；未獲同意或已終止的互動不得據此取得新更新的資料。

## 畫面操作流程

### 1. 化身與偏好設定

```text
開啟 iOS／Android／Web 應用
  ↓
以 Email 註冊並完成收件碼，或以 Google 登入（Email 未註冊時直接建帳，不需收件碼）
  ↓
同一 Email 全域檢查，已註冊／第三方同地址不可再建帳
  ↓
取得平台 Access／Refresh Token（到期依規則刷新，登出撤銷）
  ↓
個人資料：上傳／替換／刪除最多5張真人照（提醒用途 → 共用壓縮至 ≤200 KB → 私人保存）
  ↓
選擇遊戲化身：
  ├─ 免費：男性風格8款／女性風格8款內建3:4半身立繪中選1款
  └─ AI：點鎖頭進入 → 顯示第三方送照提醒 → 按「開始產生第1張」 → 每次真產出1張（最多4張）→ 可採用或再產下一張／回選先前候選 → 「採用這張」二次確認未來重生費用（MVP現階段免費） → 正式保存1張
  ↓
填寫暱稱、個性、自介、工作／職業、興趣、生活型態、價值觀、年齡／地區偏好與興趣加權
  ↓
進入配對流程（初期只有遊戲化身；雙方同意名片交換後才查閱目前真人照與工作資料）
```

### 2. 配對、劇情與好感度

```text
依條件計算契合度 → 查看候選對象 → 各自確認意向
  ├─ 尚未雙方確認 → 保持待確認
  └─ 雙方確認 → 建立專屬情境聊天室
                    ↓
             從 10 種劇情依共同興趣選擇開場
                    ↓
             人物立繪與對話框 → 3 組破冰回應 → 雙向對話
                    ↓
             回應／默契事件或問卷調整個人分數
             （本人也可隨時自由調整自己的分數）
                    ↓
             系統重算平均 → 顯示親密度區間／等級 → 判斷內容門檻
                    ↓
             各階段問卷 → 自己填寫 → 鎖頭點擊取得對方回饋內容
```

### 3. 線上遊戲、交換名片、線下約會與告白

```text
依內部親密度判定目前可用功能
  ├─ 10 至未滿 60 → 依好感度開啟 2 種小遊戲與 3 種任務
  │                   ↓
  │                 選擇可用內容 → 雙方參與 → 完成互動與結果回饋
  ├─ 達到 25 → 顯示「交換名片」→ 任一方發起邀請
  │                              ├─ 雙方同意 → 授權互看目前個人資料、工作／職業與真人照的壓縮保存版本
  │                              ├─ 待回覆 → 尚不揭露，可重送邀請
  │                              └─ 拒絕 → 不改分數，可重送邀請
  ├─ 達到 50 → 可提前使用「約會」並查看線下活動建議
  ├─ 60 至未滿 85 → 劇情推薦 5 種真實線下活動 → 定期問卷
  └─ 達到 85 → 填寫情書 → 向對方告白

約會邀請 → 對方回覆
  ├─ 雙方同意 → 個人分數各設為 65 → 重算平均
  └─ 任一方拒絕 → 個人分數各設為 50 → 重算平均
```

交換名片的 25 分只控制入口顯示，不另設掉分取消邀請或重新鎖定規則；仍須雙方同意且該輪互動未終止，不能用重送繞過同意。名片讀取沿用配對前開始建立、之後可持續更新的目前個人資料；其中包含工作／職業與**本人真人照的 200 KB 壓縮版本**，但僅在有效雙方同意後才開放受控查閱。登入 Email、精確生日、原始未壓縮照片、私人分數與登入憑證依然禁止揭露。

### 4. 隨時退出

```text
該輪互動的任一階段
  ├─ 冷卻／低好感 → 主動提示平順結束
  ├─ 明確結束語境 → 啟動結束防護
  └─ 任一方點擊「結束本輪互動」 → 即刻結束該輪
                                          ↓
                              停止後續訊息及名片交換／遊戲／約會／告白推進
                                          ↓
                                     顯示結束狀態
```
